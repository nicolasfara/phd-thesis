\chapter{Introduction}
\label{chap:introduction}

Engineering a collective system means deciding what the collective computes,
where each piece of that computation runs,
and how that placement is revised once the infrastructure has changed.
%
These three decisions are taken by unrelated means and at different moments.
The computation is written in a programming model,
the placement is fixed in a deployment descriptor before the system starts,
and its revision is left to an operator working from outside the application.

What a \ac{CAS} computes is a property of the collective.
The system is built from many autonomous entities that interact locally,
and its useful behaviour belongs to the collective they form and not to any single one of them~\cite{DBLP:journals/sttt/NicolaJW20}.
%
Its membership changes while the system runs, as entities join, leave, and fail,
and an ensemble is identified by the properties its members hold at the time~\cite{DBLP:journals/taas/NicolaLPT14}.
%
A specification therefore states what the collective achieves,
for instance that a robot team holds a formation~\cite{DBLP:journals/swarm/BrambillaFBD13}
or that the phones carried through a public event estimate how crowded it is~\cite{DBLP:journals/computer/BealPV15}.
What any single entity does follows from that specification.
%
Correctness is argued the same way, over the behaviour of the collective as membership and environment change;
self-stabilisation is one established criterion~\cite{DBLP:journals/tomacs/ViroliABDP18}.

Such a system can take advantage of being deployed across the edge-cloud continuum,
where computation can sit close to the devices that produce its data,
or on hosts with the capacity to run it.
%
The same infrastructure works against it,
since its hosts differ by orders of magnitude in capability,
join and leave without notice,
and lose connectivity to one another.
%
The program does not say which host runs which piece of it, so someone has to decide.

That decision is normally taken once and left untouched.
%
This thesis makes it a variable of the running system.
%
A macro-program, the program that states what the collective achieves,
can be partitioned into components whose collective behaviour does not depend on where each component runs;
under conditions this thesis states and proves,
the assignment of components to hosts stops being a correctness concern.
%
It becomes a choice that can be made and remade while the system runs,
on non-functional grounds alone: battery, latency, load, carbon.

The model alone does not build a system.
%
The components it partitions have to come from a program,
and today such a program is written in a single paradigm,
such as aggregate computing~\cite{VIROLI2019100486},
choreographic programming~\cite{Montesi2023chor},
or multitier programming~\cite{DBLP:journals/csur/WeisenburgerWS20}.
%
Each yields deployable units in terms that do not translate into the others.
%
Choosing a deployment and revising it as the infrastructure drifts then requires a middleware that can relocate a running component,
and a policy that says which deployment to move to.
%
This thesis develops both sides: the language support, and the platform with the policies that drive it.

\section{Context and Motivation}
\label{sec:context-and-motivation}

Latency budgets, data locality, bandwidth,
and intermittent connectivity pushed computation out of the cloud~\cite{DBLP:journals/iotj/ShiCZLX16,DBLP:journals/computer/Satyanarayanan17}.
%
The result is a continuum of hosts that runs from the microcontroller embedded in the physical world to the server rack in the data centre (\cref{sec:the-continuum,subsec:continuum-characteristics}).
%
Its topology is unstable:
devices move,
batteries drain,
links fail,
and the network partitions (\cref{subsec:network-volatility}).
%
A placement chosen when the system starts can stop being a good one as load and battery levels change,
and it can stop being satisfiable once the host it names disappears or the link to it breaks (\cref{sec:the-deployment-problem}).
%
A placement also decides how much energy the system spends.
%
Energy budgets differ by orders of magnitude between a mains-powered gateway and a battery-limited robot,
and the carbon cost of the same computation varies with where and when it runs (\cref{subsec:energy-aware-orchestration}).

This thesis mainly targets two families of collective systems on that infrastructure:
\ac{IoT} ecosystems~\cite{DBLP:journals/cn/AtzoriIM10} and robot swarms~\cite{DBLP:journals/swarm/BrambillaFBD13} (\cref{sec:target-environments}).
%
Both consist of many devices,
any of which may fail or be replaced during operation.
%
Reasoning about such a system one device at a time means redoing the correctness argument every time a device joins or leaves~\cite{DBLP:journals/sttt/NicolaJW20}.

Macroprogramming moves the unit of description to the collective:
one program states what the collective achieves, and each device's behaviour is derived from it~\cite{DBLP:journals/csur/Casadei23} (\cref{sec:macro-programming}).
%
Three paradigms realise that idea,
each deriving logical units of computation from a global specification (\cref{sec:foundational-paradigms}).
%
In aggregate computing,
the specification is a computation over a field spanning an ensemble of devices;
in choreographic programming,
it is a protocol among roles,
projected onto each participant;
in multitier programming,
it is a single program whose scopes are annotated with the tier they belong to.

None of them decides where those units run on the physical infrastructure.
%
Aggregate computing assumes every device evaluates a complete instance of the program,
even where a device is a microcontroller too small to host the runtime (\cref{sec:emerge-as-pulverisation});
endpoint projection fixes one process per role;
multitier placement is resolved at compile time.
%
In all three,
the placement on physical hosts is either implied by the execution model or fixed before the program is released.
%
On a volatile infrastructure,
hosts change after release,
so that placement keeps becoming invalid.

The three paradigms also do not compose.
%
A system can need all three:
an app supporting a public event registers participants in a multitier program,
negotiates recommendations through a choreography,
and estimates crowding with an aggregate computation (\cref{sec:multiparty-motivation}).
%
Each paradigm checks its guarantees against its own model of where computation happens.
%
Run side by side, the frameworks leave unchecked every value that crosses from one to another,
and one paradigm's code can break another's guarantee,
for instance a choreography's deadlock freedom (\cref{subsec:multiparty-challenge}).

Programs in these paradigms are also costly to write.
%
The operators of each paradigm have a semantics that must be learned before the first program runs,
and the \acp{DSL} that implement them are rare in the corpora \acp{LLM} are pretrained on (\cref{sec:llms-for-code-generation}).

Nor do the architectures used to structure distributed software let the application change where its units run while it is running (\cref{sec:architectural-paradigms}).
%
A microservice's deployment unit is a container under an orchestrator,
and moving it is an operator's action, which the application can neither express nor trigger.
%
\ac{FaaS} narrows the unit but makes it stateless,
so application state moves to backing services, usually cloud-hosted.
%
Actor runtimes keep state inside the actor and can place actors automatically,
but the placement policy belongs to the runtime and is tuned for data-centre clusters (\cref{subsec:paradigm-limitations}).

Pulverisation closes part of the placement gap.
%
Casadei et al.\ split each logical device into sensing, actuation, behaviour, state, and communication components,
each deployable wherever the continuum offers the resources it needs~\cite{DBLP:journals/fi/CasadeiPPVW20}.
%
The partitioning is fixed in advance, though:
five deployable units per logical device whatever the application computes,
and a logical device is relocated as a whole.
%
A behaviour component that runs an entire aggregate program is placed as one unit,
even when its parts have different resource needs and different natural hosts (\cref{sec:pulverization-motivation}).
%
Splitting it further has a price.
%
The guarantee that motivated pulverisation,
that what the system computes does not depend on where its components run,
has to be established again for any finer partition.

The model also says which deployments are admissible,
but not who chooses among them or on what grounds.
%
PulvReAKt, an earlier step of this work,
moved that choice into a declarative specification and made it revisable at runtime~\cite{DBLP:journals/fgcs/FarabegoliPCV24}.
%
A rule-based middleware applies the specification by moving components between hosts.
%
The five roles stayed as they were,
and the developer still has to write the rules that say which deployment to move to, and when.
%
Such rules cover only the conditions their author anticipated.
%
Re-solving the placement problem at every change does not remove that limit,
since on the continuum the topology can change faster than the problem is solved (\cref{subsec:learning-based-offloading}).

\section{Research Questions}
\label{sec:research-questions}

Three questions follow from these gaps.
%
The model comes first because the other two build on it:
the language has to produce the components the model defines,
and choosing where a component runs becomes a runtime decision only once moving it is known to leave the result unchanged.

\rqhead{rq:model}{Deployment model}
A macro-program describes the behaviour of the whole collective,
but its components run on devices with different capabilities.
%
The five-role partitioning fixes the number of deployable units before the application is known,
and the paradigms that produce these units leave their placement implicit.
%
\emph{Under what conditions can a collective macro-program be partitioned into independently deployable components so that its observable behaviour does not depend on how those components are mapped onto physical devices?}
%
An answer has to state the conditions and prove that the behaviour is invariant under them.
%
Both are given for macro-programs partitioned along their own data flow (\cref{subsec:macroprogram-dag,thm:deployment-independence}).
%
Simulations then check that different deployments of the same macro-program stabilise to the same values,
and measure how far apart they are before they do (\cref{subsec:pulverization-validation}).

\rqhead{rq:languages}{Language and coordination support}
Each of the three paradigms produces deployable components, but in terms that do not translate into one another:
a placed value, a projected role, and a field over an ensemble are different kinds of object.
%
A system built from more than one paradigm therefore cannot be pulverised as a whole.
%
Running one framework per paradigm side by side does not solve this,
because each framework's guarantees stop at its own boundary.
%
\emph{What language support lets a single program combine aggregate, choreographic, and multitier coordination, produce the deployable components the model requires, and reject at compile time the coordination errors that an ad-hoc combination allows?}
%
The type discipline that rejects these errors must be sound,
and it must still accept the programs each paradigm supports.
%
A soundness proof shows that no accepted program breaks the rules of the three paradigms (\cref{subsec:camil-formalization}).
%
A reimplementation study shows that all 46 use cases from the literature of the three paradigms can be written in the language (\cref{subsec:camil-expressivity}),
and so can three applications that mix the paradigms in one program (\cref{subsec:inter-paradigm}).

\subrqhead{rq:generation}{Generation}
Even with a sound discipline, someone still has to write the program.
%
\acp{LLM} generate code from natural language,
but the \ac{DSL} is rare in the data they are trained on.
%
\emph{Can an \ac{LLM} generate such a program from a natural-language specification, and what does it need to be told about the language for this to work?}
%
Generated programs are scored with \emph{pass@k} against eleven test cases checked in simulation (\cref{sec:llm-pipeline}).
%
Sixteen \acp{LLM} are compared at three levels of supplied knowledge,
to test whether the score rises with what a model is told more than with its size (\cref{sec:llm-evaluation}).

\rqhead{rq:deployment}{Runtime deployment decision}
Deployment independence makes all admissible deployments functionally equivalent,
but it does not say which one to choose.
%
Changes in the infrastructure eventually invalidate any choice,
so the choice must be revisable while the system runs (\cref{sec:the-deployment-problem}).
%
\emph{How can a policy, written in advance or learned from experience, choose among these deployments and revise the choice at runtime on non-functional grounds only, and what does improving one non-functional quantity cost in the others?}
%
Three hand-written policies each target one quantity, such as battery life or carbon emissions.
%
Simulations measure the gain on that quantity together with its cost in messages, latency, or convergence time,
and check that this cost stays bounded (\cref{chap:deployment-and-reconfiguration}).
%
A learned policy weighs several quantities at once through the weights of its reward.
%
Simulations vary these weights to check that the resulting deployments follow the stated trade-off (\cref{chap:heterogeneous-gnn}).

\section{Contributions}
\label{sec:contributions}

Each contribution below names the chapter that develops it, the paper it comes from, and the research question it answers.
\Cref{tab:contributions} collects this information.

\paragraph{A deployment model for macro-programs.}
A macro-program is partitioned along its own data flow into a \ac{DAG} of components,
and each component is a unit that can be deployed on its own.
%
A component is local or collective,
depending on whether its computation involves neighbouring devices.
%
The device that owns a component reaches it through a forwarding chain (\cref{sec:pulverization-abstractions}).
%
The main theorem rests on two hypotheses:
every component computes a self-stabilising function,
and the sensor state is the same along every forwarding chain.
%
Under these hypotheses,
the values at the macro-program's output ports stabilise to a result that does not depend on the deployment (\cref{thm:deployment-independence}).
%
Simulations in Alchemist~\cite{DBLP:journals/jos/PianiniMV13} compare a monolithic deployment with an offloaded one
over networks of 50, 100, and 200 mobile nodes.
%
The two deployments converge to the same result once the nodes stop moving (\cref{subsec:pulverization-validation}).
%
The partitioning and the theorem are the central technical result of the thesis.
%
They are published in~\cite{DBLP:conf/acsos/FarabegoliVC24} and answer \cref{rq:model}.
%
An earlier step of this work, the PulvReAKt middleware~\cite{DBLP:journals/fgcs/FarabegoliPCV24},
kept the original five-role partitioning
and made the assignment of components to hosts revisable at runtime through a declarative specification.
%
The five-role partitioning and the data-flow partitioning cut along different axes and can be combined (\cref{sec:pulverization-discussion}).

\paragraph{One type discipline for three coordination paradigms.}
\camil turns each paradigm into a \emph{capability}: a value that code must hold to use that paradigm's operations.
%
All paradigms share the same placement types,
so a value produced under one paradigm reaches another through its placement,
without an ad-hoc bridge (\cref{sec:capabilities-unification}).
%
The discipline is implemented in Scala~3,
using its contextual abstractions, capture checking, and separation checking,
and it is proved sound (\cref{thm:camil-soundness}).
%
The evaluation reimplements all 46 use cases collected from the multitier, choreographic, and aggregate literature.
%
Three further applications combine paradigms in a single program (\cref{sec:camil-evaluation}).
%
The design is under review~\cite{Farabegoli:2026:CaMiL}.
%
Together with the next contribution, it answers \cref{rq:languages}.

\paragraph{Differentiated communication primitives for multiparty coordination.}
Choreographic and multitier languages support several communication patterns besides point-to-point exchange.
%
Each language provides them through its own constructs,
which differ from one language to the other and can be hard to use.
%
ScalaTropy is a monadic \ac{DSL} that gives each classical pattern its own typed operation:
point-to-point, isotropic, anisotropic, and co-anisotropic communication.
%
Its types also record the architecture that a choreography targets (\cref{sec:scalatropy}).
%
In a matrix-vector product, the anisotropic primitive keeps the bytes sent by the master nearly constant as workers are added.
%
With broadcast-and-filter, the same scatter sends a number of bytes that grows linearly with the workers (\cref{subsec:scalatropy-evaluation}).
%
The design is published in~\cite{Farabegoli:2026:ScalaTropy}.

\paragraph{A body of knowledge for generating aggregate programs.}
ScaFi is an aggregate \ac{DSL} embedded in Scala,
so an \ac{LLM} easily writes ScaFi programs that compile.
%
Some of these programs still compute the wrong result,
because the model can misinterpret what operators such as \code{rep} and \code{nbr} compute at each device and round.
%
The \emph{body of knowledge} supplies the semantics of these operators.
%
It is a short operational manual, placed in the model's context at generation time.
%
It introduces each operator through a minimal program and the values that program produces over successive rounds (\cref{sec:body-of-knowledge}).
%
An entry is added only when an observed failure requires it,
and never when it would contain the solution to a test case (\cref{subsec:bok-codesign}).
%
Across sixteen models, the result depends on what the model is told, not on its size:
the largest model in the study is not the best at any knowledge level (\cref{sec:llm-evaluation}).
%
The contribution is published in~\cite{DBLP:journals/tiot/AguzziFV25} and answers \cref{rq:generation}.

\paragraph{Three hand-written reconfiguration policies.}
Three policies, each written by hand, choose a deployment and revise it at runtime (\cref{chap:deployment-and-reconfiguration}).
%
In the first, a device offloads one expensive component as soon as its battery falls below a threshold,
and moves the component again when its host becomes unreachable~\cite{DBLP:conf/acsos/FarabegoliVC24}.
%
In the second, infrastructural devices compete to host the components that application devices should not run,
and each resizes the region it leads through a collectively built field~\cite{DBLP:journals/iot/FarabegoliPCV24}.
%
The third is a planner: it searches the admissible deployments against an objective on energy and carbon,
and repeats the search as the network changes~\cite{DBLP:conf/coordination/BrogiCFFV25}.
%
Each policy reduces the quantity it targets at a bounded cost in another:
extra messages, a stabilisation transient, or added latency.
%
Each also requires a person to state in advance what a good deployment is.
%
The three policies answer the first half of \cref{rq:deployment}.

\paragraph{A learned policy for collective offloading.}
The continuum is represented as a heterogeneous graph
whose node types are application devices, edge servers, and cloud servers.
%
A \ac{GNN} over this graph is the Q-function of a deep Q-learning agent (\cref{sec:hetero-graph-state}).
%
An aggregate program runs on the same devices whose deployment is being decided,
and computes a collective summary of local density that the graph alone does not provide (\cref{subsec:collective-information}).
%
Varying the weights of a scalarised reward moves the learned policy continuously between the extremes that each single objective asks for.
%
With the collective term, they also act differently depending on a device's position:
at the fringe of a crowd, a device offloads only part of its components,
which no binary rule can do (\cref{sec:idhgql-evaluation}).
%
Because the policy is learned, no person has to state what a good deployment is.
%
This answers the second half of \cref{rq:deployment}.
%
The contribution is published in~\cite{Farabegoli:2026:HeteroGNN}.

\paragraph{A physical demonstrator.}
Project Emerge runs one aggregate program on nine mobile robots (\cref{chap:demonstrator}).
%
The robots form spatial patterns and restore them after one robot is moved by hand.
%
Each robot carries only a microcontroller, with no aggregate runtime,
and a server evaluates the program for all of them.
%
In the terms of the model,
this is a deployment where the robots are the owners and the server is their shared surrogate (\cref{sec:emerge-as-pulverisation}).
%
It supports \cref{rq:model} by showing that a deployment admitted by the model runs on real hardware.
%
It is a first step toward an end-to-end validation,
which the reconfiguration policies and quantitative measurements can extend (\cref{sec:emerge-discussion}).
%
The contribution is published in~\cite{Farabegoli:2027:ProjectEmerge}, which extends~\cite{DBLP:conf/coordination/AguzziBBCCDFPV25}.

\section{Structure of the Thesis}
\label{sec:thesis-structure}

Part~I covers the background:
the continuum and the architectural paradigms used on it (\cref{chap:edge-cloud-continuum}),
the macroprogramming paradigms and the language techniques built around them (\cref{chap:programming-models}),
and the placement, orchestration, and learning techniques that a deployment decision can draw on (\cref{chap:dynamic-reconfiguration}).
%
Part~II presents the deployment model (\cref{chap:pulverization})
and the language support that produces its components:
the two designs that unify the paradigms (\cref{chap:language-and-coordination})
and the generation of macro-programs from natural language (\cref{chap:language-based-macroprogramming}).
%
Part~III turns to the deployments themselves:
reconfiguration policies written by hand (\cref{chap:deployment-and-reconfiguration}),
a policy learned from experience (\cref{chap:heterogeneous-gnn}),
and one admissible deployment running on physical robots (\cref{chap:demonstrator}).
%
The research questions are answered in the conclusions (\cref{chap:conclusions}),
which also collect the limitations stated in each chapter and list open problems.

A reader already familiar with the continuum and with macroprogramming can start at \cref{chap:pulverization}.
