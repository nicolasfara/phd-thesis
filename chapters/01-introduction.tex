\chapter{Introduction}
\label{chap:introduction}

Engineering a collective system means deciding what the collective computes,
where each piece of that computation runs,
and how that placement is revised when the infrastructure changes.
%
These three decisions are made by unrelated means and at different times.
A programming model expresses the computation,
a deployment descriptor fixes the placement before execution,
and an operator outside the application revises it.

A \ac{CAS} consists of many autonomous entities that interact locally.
Its useful behaviour is a property of the resulting collective, not of any single entity~\cite{DBLP:journals/sttt/NicolaJW20}.
%
Its membership changes while the system runs, as entities join, leave, and fail,
and an ensemble is identified by the properties its members hold at the time~\cite{DBLP:journals/taas/NicolaLPT14}.
%
A specification therefore states what the collective achieves,
for instance that a robot team holds a formation~\cite{DBLP:journals/swarm/BrambillaFBD13}
or that crowd density at a public event is estimated from attendees' phones~\cite{DBLP:journals/computer/BealPV15}.
What any single entity does follows from that specification.
%
Correctness is assessed at the collective level as membership and the environment change;
self-stabilisation is one established criterion~\cite{DBLP:journals/tomacs/ViroliABDP18}.

Deploying such a system across the edge-cloud continuum allows computations to execute near the devices that produce their data
or on hosts with greater capacity.
%
However, this infrastructure is heterogeneous and volatile:
its hosts differ by orders of magnitude in capability,
join and leave without notice,
and lose connectivity to one another.
%
The program does not specify which host executes each part of the computation,
so the placement must be decided separately.

The placement is normally fixed once and remains unchanged during execution.
%
This thesis instead treats placement as a runtime variable.
%
A macro-program states what the collective achieves.
It can be partitioned into components whose collective behaviour does not depend on where each component executes.
This thesis states and proves conditions under which the component-to-host assignment does not affect functional correctness.
%
The assignment can then be selected and revised at runtime according only to non-functional criteria:
battery level, latency, load, and carbon emissions.

The deployment model defines the components that can be moved,
but those components must be obtained from a program.
%
Current programs generally use a single paradigm,
such as aggregate computing~\cite{VIROLI2019100486},
choreographic programming~\cite{Montesi2023chor},
or multitier programming~\cite{DBLP:journals/csur/WeisenburgerWS20}.
%
Each paradigm represents its deployable units differently,
and the representations are not directly compatible.
%
Runtime deployment also requires middleware that can relocate an executing component as the infrastructure changes.
A policy must select the next deployment.
%
This thesis develops the language support, the runtime platform, and the policies that revise deployments.

\section{Context and Motivation}
\label{sec:context-and-motivation}

Latency constraints, data locality, limited bandwidth,
and intermittent connectivity have moved computation from the cloud towards edge devices~\cite{DBLP:journals/iotj/ShiCZLX16,DBLP:journals/computer/Satyanarayanan17}.
%
The resulting continuum spans hosts from microcontrollers embedded in the physical world to server racks in the data centre (\cref{sec:the-continuum,subsec:continuum-characteristics}).
%
Its topology changes as devices move, batteries drain, links fail, and the network partitions (\cref{subsec:network-volatility}).
%
A placement chosen when the system starts can cease to meet its objective as load and battery levels change.
It can become infeasible if a required host disappears or a link fails (\cref{sec:the-deployment-problem}).
%
A placement also affects the system's energy consumption.
%
Energy budgets differ by orders of magnitude between a mains-powered gateway and a battery-limited robot,
and the carbon cost of a computation depends on where and when it executes (\cref{subsec:energy-aware-orchestration}).

This thesis mainly targets two families of collective systems on that infrastructure:
\ac{IoT} ecosystems~\cite{DBLP:journals/cn/AtzoriIM10} and robot swarms~\cite{DBLP:journals/swarm/BrambillaFBD13} (\cref{sec:target-environments}).
%
Both consist of many devices,
any of which may fail or be replaced during operation.
%
A device-level correctness argument must be reconstructed whenever a device joins or leaves~\cite{DBLP:journals/sttt/NicolaJW20}.

Macroprogramming specifies behaviour at the collective level:
one program states what the collective achieves, from which each device's behaviour is derived~\cite{DBLP:journals/csur/Casadei23} (\cref{sec:macro-programming}).
%
Three paradigms realise that idea,
each deriving logical units of computation from a global specification (\cref{sec:foundational-paradigms}).
%
Aggregate computing specifies a computation over a field spanning an ensemble of devices.
Choreographic programming specifies a protocol among roles and projects it onto each participant.
Multitier programming annotates the scopes of a single program with the tiers to which they belong.

These paradigms do not expose physical placement as a runtime decision.
%
Aggregate computing assumes every device evaluates a complete instance of the program,
even when a device is a microcontroller too small to host the runtime (\cref{sec:emerge-as-pulverisation});
endpoint projection fixes one process per role;
multitier placement is resolved at compile time.
%
Their execution models either imply the mapping to physical hosts or fix it before release.
%
On a volatile infrastructure,
changes after release can invalidate that placement.

Implementations of the three paradigms also do not compose directly.
%
A system may require all three:
an application supporting a public event registers participants in a multitier program,
negotiates recommendations through a choreography,
and estimates crowding with an aggregate computation (\cref{sec:multiparty-motivation}).
%
Each paradigm checks its guarantees against its own model of where computation happens.
%
Running the frameworks side by side leaves values that cross framework boundaries unchecked.
Operations in one framework can therefore violate another framework's guarantees,
for instance a choreography's deadlock freedom (\cref{subsec:multiparty-challenge}).

Programs in these paradigms require specialised language knowledge.
%
A developer must learn the semantics of each paradigm's operators.
Moreover, the \acp{DSL} that implement them are rare in the corpora used to pretrain \acp{LLM} (\cref{sec:llms-for-code-generation}).

Existing distributed-software architectures also do not allow an application to change the placement of its units at runtime (\cref{sec:architectural-paradigms}).
%
A microservice's deployment unit is a container under an orchestrator,
and only the operator can move it; the application can neither express nor trigger the move.
%
\ac{FaaS} uses a finer unit but treats functions as stateless,
so application state moves to backing services, usually cloud-hosted.
%
Actor runtimes keep state inside the actor and can place actors automatically,
but the runtime controls the placement policy and tunes it for data-centre clusters (\cref{subsec:paradigm-limitations}).

Pulverisation partially addresses the placement problem.
%
Casadei et al.\ split each logical device into sensing, actuation, behaviour, state, and communication components,
each deployable wherever the continuum offers the resources it needs~\cite{DBLP:journals/fi/CasadeiPPVW20}.
%
The partitioning is fixed in advance:
each logical device has five deployable units regardless of the application,
and a logical device is relocated as a whole.
%
A behaviour component that runs an entire aggregate program is placed as one unit,
even when its parts have different resource requirements and are suited to different hosts (\cref{sec:pulverization-motivation}).
%
Any finer partition must re-establish the defining guarantee of pulverisation:
the computed result does not depend on where the components execute.

The original model defines which deployments are admissible,
but not who chooses among them or on what grounds.
%
PulvReAKt, an earlier step of this work,
represented that choice in a declarative specification and allowed it to be revised at runtime~\cite{DBLP:journals/fgcs/FarabegoliPCV24}.
%
A rule-based middleware applies the specification by moving components between hosts.
%
PulvReAKt retains the five-role partitioning,
and the developer must still write rules that select a deployment and trigger each change.
%
Such rules cover only the conditions their author anticipated.
%
Repeated optimisation does not remove this limitation because the topology may change before the solver produces a new placement (\cref{subsec:learning-based-offloading}).

\section{Research Questions}
\label{sec:research-questions}

Three questions follow from these gaps.
%
The model comes first because the other two build on it:
the language has to produce the components the model defines,
and placement becomes a runtime decision only after different deployments are known to preserve the result.

\rqhead{rq:model}{Deployment model}
A macro-program describes the behaviour of the whole collective,
but its components run on devices with different capabilities.
%
The five-role partitioning fixes five deployable units for every logical device regardless of the application,
and the paradigms that produce these units leave their placement implicit.
%
\emph{Under what conditions can a collective macro-program be partitioned into independently deployable components so that its observable behaviour does not depend on how those components are mapped onto physical devices?}
%
The answer requires explicit conditions and a proof that behaviour is invariant under them.
%
For a partition along the macro-program's data flow, the thesis defines the conditions and proves the invariance (\cref{subsec:macroprogram-dag,thm:deployment-independence}).
%
Simulations check that different deployments of the same macro-program stabilise to the same values,
and measure their difference before stabilisation (\cref{subsec:pulverization-validation}).

\rqhead{rq:languages}{Language and coordination support}
Each of the three paradigms represents deployable components differently:
a placed value, a projected role, and a field over an ensemble are different kinds of object.
%
A system built from more than one paradigm therefore cannot be pulverised as a whole.
%
Running one framework per paradigm side by side does not solve this,
because each framework verifies only code written in its own paradigm.
%
\emph{What language support lets a single program combine aggregate, choreographic, and multitier coordination, produce the deployable components the model requires, and reject at compile time the coordination errors that an ad-hoc combination allows?}
%
The type discipline that rejects these errors must be sound,
and it must still accept the programs each paradigm supports.
%
A soundness proof establishes that every accepted program respects the constraints of all three paradigms (\cref{subsec:camil-formalization}).
%
The evaluation uses the language to reimplement all 46 use cases from the literature of the three paradigms (\cref{subsec:camil-expressivity}),
together with three applications that mix the paradigms in one program (\cref{subsec:inter-paradigm}).

\subrqhead{rq:generation}{Generation}
A sound discipline does not remove the need to write the program.
%
\acp{LLM} generate code from natural language,
but the \ac{DSL} is rare in their training data.
%
\emph{Can an \ac{LLM} generate such a program from a natural-language specification, and what does it need to be told about the language for this to work?}
%
Generated programs are evaluated using \emph{pass@k} against eleven test cases run in simulation (\cref{sec:llm-pipeline}).
%
Sixteen \acp{LLM} are compared at three levels of supplied knowledge,
to test whether the score depends more on supplied knowledge than on model size (\cref{sec:llm-evaluation}).

\rqhead{rq:deployment}{Runtime deployment decision}
Deployment independence makes all admissible deployments functionally equivalent,
but it does not say which one to choose.
%
Infrastructure changes can invalidate a fixed deployment,
so the system must be able to revise it at runtime (\cref{sec:the-deployment-problem}).
%
\emph{How can a policy, written in advance or learned from experience, choose among these deployments and revise the choice at runtime on non-functional grounds only, and what does improving one non-functional quantity cost in the others?}
%
Three hand-written policies each target one quantity, such as battery life or carbon emissions.
%
Simulations measure the improvement in the target quantity and its effect on message count, latency, or convergence time,
and check that the secondary cost remains bounded (\cref{chap:deployment-and-reconfiguration}).
%
A learned policy combines several quantities in a weighted reward.
%
Simulations vary these weights to check that the resulting deployments reflect the stated trade-off (\cref{chap:heterogeneous-gnn}).

\section{Contributions}
\label{sec:contributions}

Each contribution below identifies the chapter that develops it, its associated publication, and the research question it answers.
\Cref{tab:contributions} summarises this information.

\paragraph{A deployment model for macro-programs.}
A macro-program is partitioned along its own data flow into a \ac{DAG} of independently deployable components.
%
A component is local if its computation involves one device and collective if it involves neighbouring devices.
%
A forwarding chain connects the device that owns a component to the host that executes it (\cref{sec:pulverization-abstractions}).
%
The main theorem assumes that
every component computes a self-stabilising function,
and the sensor state is the same along every forwarding chain.
%
Under these hypotheses,
the values at the macro-program's output ports stabilise to a result that does not depend on the deployment (\cref{thm:deployment-independence}).
%
Simulations in Alchemist~\cite{DBLP:journals/jos/PianiniMV13} compare a monolithic deployment with an offloaded deployment
in networks of 50, 100, and 200 mobile nodes.
%
The two deployments converge to the same result once the nodes stop moving (\cref{subsec:pulverization-validation}).
%
The partitioning and the theorem constitute the central technical result of the thesis.
%
They are published in~\cite{DBLP:conf/acsos/FarabegoliVC24} and answer \cref{rq:model}.
%
The PulvReAKt middleware, an earlier step of this work~\cite{DBLP:journals/fgcs/FarabegoliPCV24},
retains the original five-role partitioning
and makes the component-to-host assignment revisable at runtime through a declarative specification.
%
The five-role partitioning and the data-flow partitioning cut along different axes and can be combined (\cref{sec:pulverization-discussion}).

\paragraph{One type discipline for three coordination paradigms.}
\camil turns each paradigm into a \emph{capability}: a value that code must hold to use that paradigm's operations.
%
All paradigms share the same placement types,
so a value produced under one paradigm reaches another through its placement,
without an ad-hoc bridge (\cref{sec:capabilities-unification}).
%
The Scala~3 implementation uses contextual abstractions, capture checking, and separation checking.
The discipline is proved sound (\cref{thm:camil-soundness}).
%
The evaluation reimplements all 46 use cases collected from the multitier, choreographic, and aggregate literature.
%
Three further applications combine paradigms in a single program (\cref{sec:camil-evaluation}).
%
The design is under review~\cite{Farabegoli:2026:CaMiL}.
%
Together, \camil and ScalaTropy answer \cref{rq:languages}.

\paragraph{Differentiated communication primitives for multiparty coordination.}
Choreographic and multitier languages support several communication patterns besides point-to-point exchange.
%
Each language exposes different constructs,
and some patterns are encoded indirectly rather than represented by dedicated operations.
%
ScalaTropy is a monadic \ac{DSL} that gives each classical pattern its own typed operation:
point-to-point, isotropic, anisotropic, and co-anisotropic communication.
%
Its types also record the architecture that a choreography targets (\cref{sec:scalatropy}).
%
In a matrix-vector product, the anisotropic primitive keeps the bytes sent by the master nearly constant as workers are added.
%
With broadcast-and-filter, the same scatter sends a number of bytes that grows linearly with the workers (\cref{subsec:scalatropy-evaluation}).
%
The design is published in~\cite{Farabegoli:2026:ScalaTropy}.

\paragraph{A body of knowledge for generating aggregate programs.}
ScaFi is an aggregate \ac{DSL} embedded in Scala,
and an \ac{LLM} can generate ScaFi programs that compile.
%
Some of these programs still compute the wrong result,
because the model can misinterpret what operators such as \code{rep} and \code{nbr} compute at each device and round.
%
The \emph{body of knowledge} supplies the semantics of these operators.
%
It is a short operational manual, placed in the model's context at generation time.
%
It introduces each operator through a minimal program and the values that program produces over successive rounds (\cref{sec:body-of-knowledge}).
%
An entry is added only when an observed failure requires it,
and never when it would contain the solution to a test case (\cref{subsec:bok-codesign}).
%
Across sixteen models, the result depends on what the model is told, not on its size:
the largest model in the study is not the best at any knowledge level (\cref{sec:llm-evaluation}).
%
The contribution is published in~\cite{DBLP:journals/tiot/AguzziFV25} and answers \cref{rq:generation}.

\paragraph{Three hand-written reconfiguration policies.}
Three policies, each written by hand, choose a deployment and revise it at runtime (\cref{chap:deployment-and-reconfiguration}).
%
In the first, a device offloads one expensive component as soon as its battery falls below a threshold,
and moves the component again when its host becomes unreachable~\cite{DBLP:conf/acsos/FarabegoliVC24}.
%
In the second, infrastructural devices compete to host the components that application devices should not run,
and each resizes the region it leads through a collectively built field~\cite{DBLP:journals/iot/FarabegoliPCV24}.
%
The third is a planner: it searches the admissible deployments using an objective defined over energy and carbon,
and repeats the search as the network changes~\cite{DBLP:conf/coordination/BrogiCFFV25}.
%
Each policy improves its target quantity while bounding a secondary cost:
extra messages, a stabilisation transient, or added latency.
%
Each also requires a developer to define in advance what makes a deployment desirable.
%
The three policies answer the first half of \cref{rq:deployment}.

\paragraph{A learned policy for collective offloading.}
The continuum is represented as a heterogeneous graph
whose node types are application devices, edge servers, and cloud servers.
%
A \ac{GNN} over this graph is the Q-function of a deep Q-learning agent (\cref{sec:hetero-graph-state}).
%
The application devices also execute an aggregate program that computes a collective summary of local density,
which the graph alone does not provide (\cref{subsec:collective-information}).
%
Changing the weights of a scalarised reward yields policies that vary continuously between the single-objective extremes.
%
Including the collective term makes the selected action depend on a device's position:
at the fringe of a crowd, a device offloads only part of its components,
which no binary rule can do (\cref{sec:idhgql-evaluation}).
%
Training the policy from experience removes the need for a person to define a desirable deployment in advance.
%
This answers the second half of \cref{rq:deployment}.
%
The contribution is published in~\cite{Farabegoli:2026:HeteroGNN}.

\paragraph{A physical demonstrator.}
Project Emerge runs one aggregate program on nine mobile robots (\cref{chap:demonstrator}).
%
The robots form spatial patterns and restore them after one robot is moved by hand.
%
Each robot carries only a microcontroller, with no aggregate runtime,
and a server evaluates the program for all of them.
%
Under the model,
the robots own the components and the server is their shared surrogate (\cref{sec:emerge-as-pulverisation}).
%
It supports \cref{rq:model} by showing that a deployment admitted by the model runs on real hardware.
%
The demonstrator is limited to this realisability result;
end-to-end validation would also need to exercise reconfiguration policies and report quantitative measurements (\cref{sec:emerge-discussion}).
%
The contribution is reported in~\cite{Farabegoli:2027:ProjectEmerge}, an extension of~\cite{DBLP:conf/coordination/AguzziBBCCDFPV25}.

\section{Structure of the Thesis}
\label{sec:thesis-structure}

Part~I covers the background:
the continuum and the architectural paradigms used on it (\cref{chap:edge-cloud-continuum}),
the macroprogramming paradigms and the language techniques built around them (\cref{chap:programming-models}),
and the placement, orchestration, and learning techniques used to select deployments (\cref{chap:dynamic-reconfiguration}).
%
Part~II presents the deployment model (\cref{chap:pulverization})
and the language support that produces its components:
the language and coordination support (\cref{chap:language-and-coordination})
and the generation of macro-programs from natural language (\cref{chap:language-based-macroprogramming}).
%
Part~III studies deployment and reconfiguration:
reconfiguration policies written by hand (\cref{chap:deployment-and-reconfiguration}),
a policy learned from experience (\cref{chap:heterogeneous-gnn}),
and one admissible deployment running on physical robots (\cref{chap:demonstrator}).
%
Answers to the research questions, a synthesis of the limitations stated in each chapter,
and open problems are given in \cref{chap:conclusions}.

A reader already familiar with the continuum and with macroprogramming can start at \cref{chap:pulverization}.
