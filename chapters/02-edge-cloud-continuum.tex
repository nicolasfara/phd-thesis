\chapter{The Edge-Cloud Continuum and Its Architectural Paradigms}
\label{chap:edge-cloud-continuum}

\section{The Edge-Cloud Continuum}
\label{sec:the-continuum}

Cloud computing's centralised model -- offloading computation to large, remote data centres~\cite{DBLP:journals/cacm/ArmbrustFGJKKLPRSZ10} -- runs into structural limits when applications require low latency,
strict data locality,
bandwidth efficiency,
or operation under intermittent connectivity~\cite{DBLP:journals/iotj/ShiCZLX16,DBLP:journals/computer/Satyanarayanan17}.
%
Early work on mobile cloud computing already framed the tension between the resource-richness of the cloud and the constraints of end devices in terms of \emph{application partitioning}:
deciding which parts of a computation should run locally and which should be offloaded~\cite{DBLP:journals/jnca/LiuASGBQ15}.
%
The \emph{edge-cloud continuum} generalises this tension: rather than a binary split between ``device'' and ``cloud'',
it denotes a spectrum of computing and networking resources distributed between the two extremes,
over which computations can be placed,
moved,
and re-placed as conditions change,
as depicted in \cref{fig:edge-cloud-continuum}.
%
This section characterises the continuum as an architectural setting.
%
Later sections introduce the target environments that populate it and review the architectural paradigms available to build systems on top of it;
the programming and coordination abstractions suited to these settings are then the subject of \cref{chap:programming-models}.

\subsection{Evolution and Topology}
\label{subsec:continuum-evolution}

The continuum did not emerge fully formed:
it is the result of computing infrastructure moving away from the cloud in stages.
%
Cloudlets first proposed placing a single hop of resource-rich,
virtualised infrastructure between mobile devices and the cloud,
trading the latency of a wide-area link for that of a local one~\cite{DBLP:journals/pervasive/SatyanarayananBCD09}.
%
Fog computing generalised this idea into a hierarchical layer of gateways and micro data centres between data sources and the cloud,
driven by the amount and spread of IoT traffic~\cite{DBLP:conf/sigcomm/BonomiMZA12}.
%
Edge computing pushed the same idea further,
placing computation directly at or near the devices that generate the data rather than at an intermediate layer~\cite{DBLP:journals/iotj/ShiCZLX16,DBLP:journals/computer/Satyanarayanan17}.
%
These proposals were developed largely independently,
under many related names -- cloudlet, fog, mist, cloud-to-thing continuum -- and only recently have literature reviews tried to bring them together under one definition~\cite{DBLP:journals/access/MoreschiniPLNHT22}.

Automatic deployment of distributed software has long been recognised as a distinct engineering concern,
with dedicated models,
tools,
and open problems~\cite{DBLP:journals/jss/ArcangeliBL15}.
%
More recent work treats deployment for the continuum not as a one-off placement decision,
but as a process that can be reconfigured at any time.
%
This matches an older argument in software architecture research: a system's components and connectors should be built to change while running,
not patched together as an afterthought~\cite{DBLP:conf/icse/KramerM07}.
%
Pulverisation, for instance, breaks applications into fine-grained units whose deployment can be reconfigured at runtime,
for any kind of application~\cite{DBLP:journals/fgcs/FarabegoliPCV24}.
%
Within the narrower field of collective and self-organising systems, the same idea appears at the level of macro-programming:
declarative, high-level specifications state where collective behaviour should run across cloud and edge~\cite{DBLP:conf/acsos/FarabegoliVC24},
and simulation methods estimate the deployment performance of collective services once they are spread across such a topology~\cite{DBLP:journals/iotj/CasadeiFPPSV22}.
%
The resulting topology is best seen not as the fixed stack of layers suggested by the cloud/fog/edge terms,
but as a loosely structured, dynamically changing graph of heterogeneous nodes,
in which the same device can act as an edge node for one application and as a relay for another.

\subsection{Characteristics and Infrastructure Heterogeneity}
\label{subsec:continuum-characteristics}

Nodes on the continuum differ radically in computational capacity,
memory,
energy budget,
and software stack.
%
At one extreme,
microcontrollers with a few kilobytes of memory run a single sensing task under a real-time operating system,
or under no operating system at all;
at the other,
cloud servers run general-purpose operating systems and draw on effectively elastic resources.
%
This spread in resources has architectural consequences:
different classes of devices are programmed through different software component models,
historically classified along dimensions such as composition mechanisms,
deployment units,
and binding times~\cite{DBLP:journals/tse/CrnkovicSVC11}.
%
A component model built for a resource-rich server,
with dynamic loading and network-transparent binding,
does not transfer to a microcontroller that has neither.

The links connecting these nodes are just as heterogeneous:
short-range radio,
cellular,
and wired connections coexist on the same continuum,
each with its own bandwidth,
latency,
and reliability profile.
%
This is a structural property of the infrastructure,
distinct from the temporal changes in connectivity discussed in \cref{subsec:network-volatility} --
even a stationary deployment over a stable topology must reconcile a sensor on a low-power radio link with a gateway on fibre.
%
The application-partitioning taxonomy introduced in \cref{sec:the-continuum}~\cite{DBLP:journals/jnca/LiuASGBQ15} captures the consequence of this asymmetry from the programmer's side,
distinguishing offloading strategies by what is partitioned,
when,
and under which constraints.
%
Device and network heterogeneity therefore compound,
and the programming and deployment abstractions examined in \cref{chap:programming-models} and \cref{sec:architectural-paradigms} have to accommodate both at once,
rather than assume a uniform target for computation.

Energy is a further axis of heterogeneity that does not track computational capacity.
%
A gateway can be mains-powered and computationally modest,
while a mobile robot or drone carries a powerful system-on-chip on a battery budget measured in minutes,
and a sensor node may run indefinitely on a harvested,
intermittent supply.
%
Placement decisions must therefore account for how long and how often a node can sustain a computation,
not only what it is capable of computing. \Cref{subsec:energy-aware-orchestration} returns to this as a first-class deployment concern.

\subsection{Network Volatility and Partitioning}
\label{subsec:network-volatility}

The heterogeneity discussed in \cref{subsec:continuum-characteristics} is a static property of the infrastructure;
on top of it,
the continuum also changes over time.
%
Devices move,
radio links drop,
and nodes disappear and reappear as they run out of range or out of power --
towards the edge this becomes a defining characteristic of the network.
%
This is not a new problem in networking:
delay/disruption-tolerant networking gave up on the assumption of an end-to-end path decades ago,
buffering messages at intermediate nodes and forwarding them opportunistically as contact becomes available~\cite{DBLP:conf/sigcomm/Fall03}.
%
Opportunistic networking took the same idea into mobile ad hoc settings,
where a route is not computed in advance but assembled hop by hop as devices happen to come within range of one another~\cite{DBLP:journals/cm/PelusiPC06}.

Drone swarms and other ad hoc networks are a particularly extreme case of this volatility.
%
A flying ad hoc network (FANET) is more volatile than a ground-based ad hoc network for a simple reason: its nodes move in three dimensions and at speed,
so links form and break faster than most routing protocols were designed for.
%
FANETs are consequently studied as a networking class of their own,
with dedicated mobility models and protocols~\cite{DBLP:journals/adhoc/BekmezciST13}.
%
Surveys of UAV communication networks routinely list delay-tolerant,
store-carry-forward schemes as one of the standard design options,
alongside clustering and cooperative relaying~\cite{DBLP:journals/comsur/GuptaJV16}.
%
Ground robot swarms and dense IoT deployments (\cref{subsec:swarm-robotics} and \cref{subsec:iot-systems}) face a milder version of the same problem,
since packing enough autonomous devices into a short-range ad hoc network is enough on its own to keep the topology dynamic.

Coordination mechanisms for the continuum need to consider such dynamic topologies as a first-class concern.
%be built with this in mind from the start,
% rather than have it patched in later.
%
Time-fluid, field-based coordination, for instance, turns scheduling into something the collective itself can program and adapt to conditions,
instead of assuming synchrony by default~\cite{DBLP:journals/lmcs/PianiniCVMZ21}.
%
Decentralised proximity-aware clustering does something similar for a different problem:
it organises a collective or federated learning process around whichever neighbours happen to be reachable at a given moment,
rather than around a graph fixed in advance~\cite{DBLP:journals/iot/DominiFAVE26}.
%
% Both examples point to a theme that recurs throughout the thesis:
% handling network volatility well is as much a concern for the programming model as it is for the infrastructure underneath it.

\section{Target Environments: IoT Ecosystems and Robot Swarms}
\label{sec:target-environments}

Cyber-physical systems and robot swarms are natural stress tests for the continuum characterised in \cref{sec:the-continuum}:
they combine physical embodiment,
mobility,
and energy constraints with a need for both local autonomy and collective coordination,
exercising its heterogeneity and volatility at once.
%
This section surveys two concrete instances of such pervasive environments,
IoT ecosystems (\cref{subsec:iot-systems}) and swarm robotics (\cref{subsec:swarm-robotics}),
frames them as instances of the broader class of collective adaptive systems (\cref{subsec:collective-adaptive-systems}),
and closes by drawing out the deployment and coordination challenges they share (\cref{subsec:environment-challenges}),
which motivate the architectural paradigms reviewed next, in \cref{sec:architectural-paradigms}.

\subsection{Pervasive IoT Systems}
\label{subsec:iot-systems}

IoT ecosystems~\cite{DBLP:journals/cn/AtzoriIM10} populate the continuum with large numbers of sensing and actuating devices,
connected through the heterogeneous links discussed in \cref{subsec:continuum-characteristics}.
%
Individually, such devices run comparatively simple sensing or actuation loops;
what makes an IoT deployment interesting is the aggregate,
collective behaviour that emerges once many of them are coordinated toward a shared goal,
such as monitoring a building,
a field,
or a city district.
%
The notion of \emph{aggregate process} was introduced precisely to capture this shift in perspective:
a concurrent, self-organising computation whose execution and interactions are sustained by a dynamic team of devices,
and whose spatial region and set of participants can vary opportunistically over time~\cite{CASADEI2021104081}.
%
Programming at the level of the aggregate rather than the individual device is,
in this view,
a consequence of the continuum's own volatility (\cref{subsec:network-volatility}) rather than a stylistic choice:
the team of devices sustaining a given computation cannot be fixed in advance if the devices themselves come and go.

Realising this view in practice requires deciding,
continuously,
which devices host which part of the computation.
%
Dynamic IoT deployment reconfiguration has been studied as a global-level self-organisation problem,
in which the ecosystem itself -- rather than an external orchestrator -- decides how to redistribute computation as devices join,
leave,
or change state~\cite{DBLP:journals/iot/FarabegoliPCV24}.
%
Because trying out reconfiguration strategies on physical IoT deployments is costly and slow,
a complementary line of work develops simulation-based methodologies to estimate the deployment performance of smart collective services before they run on real infrastructure~\cite{DBLP:journals/iotj/CasadeiFPPSV22}.
%
Both directions treat deployment as a first-class, ongoing concern rather than a one-off placement decision,
consistent with the general argument already made for the continuum in \cref{subsec:continuum-evolution}.

\subsection{Swarm Robotics}
\label{subsec:swarm-robotics}

Swarm robotics studies large groups of relatively simple robots that achieve complex,
useful behaviour through local interaction and self-organisation rather than central control,
a design philosophy surveyed from both a swarm-engineering and a systems perspective~\cite{DBLP:journals/swarm/BrambillaFBD13,DBLP:journals/sensors/DiasSFVCP21}.
%
As anticipated in \cref{subsec:network-volatility},
a robot swarm is at once an instance of the continuum and one of its most volatile settings:
the ad hoc network connecting the robots is itself a side effect of their movement,
so the topology a swarm application must cope with changes as fast as the robots do.
%
Fault-tolerant cooperation among multiple robots predates this framing:
ALLIANCE organised a team of behaviour-based robots so that tasks could be reassigned and individual failures tolerated without central coordination~\cite{parker1998alliance},
anticipating by two decades the self-organisation requirements now associated with the continuum.

Programming a swarm directly in terms of individual robot behaviours does not scale past a handful of units,
which motivated dedicated languages and frameworks that let a programmer express swarm behaviour at a higher level.
%
Buzz provides swarm-oriented primitives -- neighbourhood queries,
virtual stigmergy,
robot-to-robot synchronisation -- on top of a small imperative core~\cite{buzz-robot},
while Meld takes a declarative, logic-based approach and derives single-robot behaviour by compiling rules stated over the whole ensemble~\cite{meld-robot}.
%
Voltron pushes team-level programming into resource-constrained sensor networks,
targeting drones directly~\cite{voltron-robot},
and actor-based abstractions have been proposed as a general structuring principle for swarm robotic software,
isolating per-robot state behind message passing~\cite{DBLP:conf/iros/YiDLD0WY20} --
the actor model itself is treated in more general terms in \cref{subsec:actor-model-edge}.
%
Existing robotics middleware has been extended in the same direction,
as with the swarm-specific package built on top of ROS~\cite{rosMicros_swarm_frameworkWiki},
and toolkits such as PySwarming lower the barrier further by packaging common swarm algorithms for direct reuse~\cite{DBLP:journals/jossw/AndradeFS23}.

This body of work has been validated largely on a shared set of experimental platforms.
%
The Kilobot is a low-cost robot designed specifically to be deployed in the large numbers that swarm algorithms assume~\cite{DBLP:conf/icra/RubensteinAN12},
and the Kilogrid testbed extends it with a virtual sensing and communication substrate that lets a swarm of Kilobots be reconfigured between experiments without touching the hardware~\cite{valentini2018kilogrid}.
%
Where physical swarms of the required size are impractical,
the ARGoS~\cite{pinciroli2012argos} and Webots~\cite{Michel2004} simulators provide the modular,
multi-engine infrastructure needed to evaluate swarm algorithms at scale before -- or instead of -- deploying them on real robots.

\subsection{Collective Adaptive Systems}
\label{subsec:collective-adaptive-systems}

IoT ecosystems and robot swarms are best understood as two instances of a broader class,
termed \emph{Collective Adaptive Systems} (CAS) in a dedicated strand of the software engineering literature:
systems composed of large numbers of autonomous, interacting entities whose collective behaviour must remain correct and useful despite continuous change in membership,
environment,
and goals~\cite{DBLP:journals/sttt/NicolaJW20}.
%
Framed this way, the aggregate processes of \cref{subsec:iot-systems} and the self-organising robot teams of \cref{subsec:swarm-robotics} are two applications of the same underlying requirement:
a CAS cannot assume a fixed set of participants or a fixed topology,
so its correctness has to be argued about the collective's behaviour under change,
not about any single entity in isolation.

Meeting this requirement calls for architecture models that treat reconfiguration as an intrinsic, formally grounded part of system behaviour,
in the sense already argued for self-managed systems in general in \cref{subsec:continuum-evolution}~\cite{DBLP:conf/icse/KramerM07}.
%
The DReAM framework instantiates this idea for CAS specifically,
modelling dynamic reconfiguration as part of a system's architecture rather than as an exception to it,
with a formal semantics that supports reasoning about the system as it reconfigures~\cite{DBLP:journals/sttt/NicolaMS20}.
%
At the programming level, a recent survey situates \emph{macroprogramming} -- specifying the behaviour of a collective as a whole,
rather than programming individual nodes -- as the dominant strategy for engineering CAS at scale~\cite{DBLP:journals/csur/Casadei23};
\cref{chap:programming-models} examines in detail the programming models that realise this strategy,
including the aggregate computing approach already introduced through the aggregate process notion of \cref{subsec:iot-systems}.

\subsection{Deployment and Coordination Challenges}
\label{subsec:environment-challenges}

IoT ecosystems and robot swarms, despite their different physical form, put pressure on the continuum in the same two ways.
%
First, both must place computation and coordination logic onto a set of nodes that is heterogeneous in the sense of \cref{subsec:continuum-characteristics} -- constrained sensor nodes next to gateways and cloud servers -- and mobile or intermittently connected in the sense of \cref{subsec:network-volatility},
so that no placement decision can be assumed to remain valid for long.
%
Second, both need the coordination logic itself,
not only its placement,
to keep working as the set of participating devices changes:
the aggregate processes of \cref{subsec:iot-systems} and the ad hoc robot teams of \cref{subsec:swarm-robotics} are two answers to the same problem of coordinating a collective whose membership is not fixed in advance.

Deployment for such systems has to be revisited continuously rather than decided once,
echoing the general argument made for the continuum at large in \cref{subsec:continuum-evolution}.
%
Fine-grained, runtime-reconfigurable deployment models such as pulverisation show one way of acting on this argument directly,
by making the unit of deployment small enough,
and its reconfiguration cheap enough,
to be revisited as often as the environment demands~\cite{DBLP:journals/fgcs/FarabegoliPCV24}.
%
Whether the architectural paradigms already used to structure distributed applications can support this degree of deployment flexibility is the question taken up next,
in \cref{sec:architectural-paradigms}.

\section{Architectural Paradigms for Pervasive Systems}
\label{sec:architectural-paradigms}

Mainstream software architecture offers several paradigms for structuring distributed applications -- microservices, Function-as-a-Service (FaaS), and the actor model chief among them -- each of which has been adapted, with varying success, to edge and pervasive settings. This section reviews these paradigms as currently applied at the edge and then argues that they fall short of the fine-grained, dynamic deployment needs identified in \cref{sec:target-environments}.

\subsection{Microservices and FaaS at the Edge}
\label{subsec:microservices-faas-edge}

Microservices~\cite{DBLP:books/sp/17/DragoniGLMMMS17} and FaaS~\cite{DBLP:books/sp/17/BaldiniCCCFIMMRSS17} both decompose applications into independently deployable units, which makes them attractive starting points for edge deployment, while classification frameworks for software component models offer the conceptual vocabulary to compare them against edge-specific alternatives~\cite{DBLP:journals/tse/CrnkovicSVC11}.

\subsection{The Actor Model at the Edge}
\label{subsec:actor-model-edge}

The actor model~\cite{DBLP:conf/ijcai/HewittBS73}, with its emphasis on isolated, message-passing units of computation, has also been proposed as a structuring principle for pervasive systems, as illustrated by actor-based frameworks for swarm robotics~\cite{DBLP:conf/iros/YiDLD0WY20}.

\subsection{Limitations for Fine-Grained, Dynamic Deployment}
\label{subsec:paradigm-limitations}

% TODO(canovaccio): expand into full prose.
Despite this adaptability, microservices, FaaS, and actor-based architectures largely retain deployment granularities and lifecycles designed for comparatively stable cloud infrastructure: units of deployment are coarser, and re-placement across nodes is typically not a first-class, runtime-programmable operation. This confirms, at the architectural level, the partitioning and deployment limitations already identified in \cref{subsec:continuum-evolution}, \cref{subsec:continuum-characteristics}, and \cref{subsec:environment-challenges}. Pulverisation is presented directly as a response to this gap, decomposing applications into much finer-grained units whose deployment can be declaratively reconfigured at runtime~\cite{DBLP:journals/fgcs/FarabegoliPCV24} -- a direction this thesis builds upon and develops in full in \cref{chap:pulverization}, after \cref{chap:dynamic-reconfiguration} takes up the runtime and orchestration side of the same gap.
