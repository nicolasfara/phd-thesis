\chapter{Architectures for the Edge-Cloud Continuum}
\label{chap:edge-cloud-continuum}

Every contribution of this thesis targets the computing infrastructure between cloud data centres and devices embedded in the physical world.
%
The two target systems considered here are \ac{IoT} ecosystems and robot swarms.
These systems require fine-grained deployment and runtime reconfiguration across heterogeneous hosts.
%
This chapter examines the infrastructure, the target systems, and the architectural approaches used to deploy their computations.

\section{The Edge-Cloud Continuum}
\label{sec:the-continuum}

Cloud computing uses a centralised model in which computation is offloaded to large, remote data centres~\cite{DBLP:journals/cacm/ArmbrustFGJKKLPRSZ10}.
This model has structural limits when applications require low latency,
strict data locality,
bandwidth efficiency,
or operation under intermittent connectivity~\cite{DBLP:journals/iotj/ShiCZLX16,DBLP:journals/computer/Satyanarayanan17}.
%
Early work on mobile cloud computing framed the difference between abundant cloud resources and constrained end devices in terms of \emph{application partitioning}:
deciding which parts of a computation should run locally and which should be offloaded~\cite{DBLP:journals/jnca/LiuASGBQ15}.
%
The \emph{edge-cloud continuum} generalises this distinction beyond a binary split between ``device'' and ``cloud''.
It comprises computing and networking resources distributed between these two extremes.
Computations can be placed and moved across these resources as conditions change (\cref{fig:edge-cloud-continuum}).

\subsection{Cloudlets, Fog, and Edge Computing}
\label{subsec:continuum-evolution}

The continuum emerged in stages as computing infrastructure moved closer to end devices.
%
The cloudlet model placed resource-rich,
virtualised infrastructure one network hop from mobile devices,
trading the latency of a wide-area link for that of a local one~\cite{DBLP:journals/pervasive/SatyanarayananBCD09}.
%
Fog computing generalised this idea into a hierarchical layer of gateways and micro data centres between data sources and the cloud,
driven by the amount and spread of \ac{IoT} traffic~\cite{DBLP:conf/sigcomm/BonomiMZA12}.
%
Edge computing pushed the same idea further,
placing computation directly at or near the devices that generate the data~\cite{DBLP:journals/iotj/ShiCZLX16,DBLP:journals/computer/Satyanarayanan17}.
%
These proposals were developed largely independently under related names such as cloudlet, fog, mist, and cloud-to-thing continuum.
Recent literature reviews have sought to place them under a common definition~\cite{DBLP:journals/access/MoreschiniPLNHT22}.

Automatic deployment of distributed software has long been recognised as a distinct engineering concern,
with dedicated models,
tools,
and open problems~\cite{DBLP:journals/jss/ArcangeliBL15}.
%
More recent work studies how to revise deployment while an application runs.
%
This matches an older argument in software architecture research: a system's components and connectors should be built to change while running~\cite{DBLP:conf/icse/KramerM07}.
%
Pulverisation, for instance, divides an application into fine-grained units whose deployment can be reconfigured at run time across application domains~\cite{DBLP:journals/fi/CasadeiPPVW20,DBLP:journals/fgcs/FarabegoliPCV24}.
%
Research on collective and self-organising systems also applies this idea at the macroprogramming level.
Declarative, high-level specifications state where collective behaviour should run across cloud and edge~\cite{DBLP:conf/acsos/FarabegoliVC24}.
Simulation methods then estimate the deployment performance of collective services distributed across this topology~\cite{DBLP:journals/iotj/CasadeiFPPSV22}.
%
As these infrastructures have developed and been combined,
the cloud/fog/edge terminology has come to describe roles within a shared infrastructure.
The continuum is a loosely structured, dynamically changing graph of heterogeneous nodes
in which the same device can act as an edge node for one application and as a relay for another.

\subsection{Infrastructure Heterogeneity}
\label{subsec:continuum-characteristics}

Nodes on the continuum differ substantially in computational capacity,
memory,
energy budget,
and software stack.
%
At one extreme,
microcontrollers with a few kilobytes of memory run a single sensing task under a real-time operating system,
or under no operating system at all;
at the other,
cloud servers run general-purpose operating systems and draw on effectively elastic resources.
%
This spread in resources has architectural consequences:
different classes of devices are programmed through different software component models,
historically classified along dimensions such as composition mechanisms,
deployment units,
and binding times~\cite{DBLP:journals/tse/CrnkovicSVC11}.
%
A component model designed for a resource-rich server may depend on dynamic loading and network-transparent binding.
It is unsuitable for a microcontroller that supports neither.

The links connecting these nodes are equally heterogeneous:
short-range radio,
cellular,
and wired connections coexist on the same continuum,
each with its own bandwidth,
latency,
and reliability profile.
%
Even a stationary deployment over a stable topology must reconcile a sensor on a low-power radio link with a gateway on fibre.
%
These differences affect how a program can be partitioned across hosts.
Liu et al.~\cite{DBLP:journals/jnca/LiuASGBQ15} classify offloading strategies by what is partitioned,
when,
and under which constraints.

Energy is another axis of heterogeneity and does not correlate directly with computational capacity.
%
A gateway can be mains-powered and computationally modest,
while a mobile robot or drone carries a powerful system-on-chip on a battery budget measured in minutes,
and a sensor node may run indefinitely on a harvested,
intermittent supply.
%
Placement decisions must therefore account for a node's computational capacity and for how long and how often it can sustain a computation.


\subsection{Network Volatility and Partitioning}
\label{subsec:network-volatility}

Resources and connectivity also change over time.
%
Devices move,
radio links drop,
and nodes disappear and reappear as they run out of range or power.
Such changes are a defining characteristic of networks towards the edge.
%
Delay/disruption-tolerant networking has long addressed this problem without assuming that an end-to-end path exists.
It buffers messages at intermediate nodes and forwards them opportunistically when contact becomes available~\cite{DBLP:conf/sigcomm/Fall03}.
%
Opportunistic networking applies the same principle to mobile ad hoc settings,
where a route is assembled hop by hop as devices come within range of one another~\cite{DBLP:journals/cm/PelusiPC06}.

Drone swarms are an extreme case of this volatility.
%
A \ac{FANET} is more volatile than a ground-based ad hoc network because its nodes move rapidly in three dimensions,
so links form and break faster than most routing protocols were designed for.
%
\acp{FANET} are therefore treated as a separate class of network,
with dedicated mobility models and protocols~\cite{DBLP:journals/adhoc/BekmezciST13}.
%
Surveys of \ac{UAV} communication networks routinely list delay-tolerant,
store-carry-forward schemes as one of the standard design options,
alongside clustering and cooperative relaying~\cite{DBLP:journals/comsur/GuptaJV16}.
%
Ground robot swarms and dense \ac{IoT} deployments face the same problem to a lesser degree,
since a short-range ad hoc network of many autonomous devices keeps the topology dynamic on its own.

Coordination mechanisms for the continuum must treat dynamic topology as a primary concern.
%
Time-fluid, field-based coordination, for instance, allows a collective program to adapt its execution schedule to current conditions~\cite{DBLP:journals/lmcs/PianiniCVMZ21}.
%
Decentralised proximity-aware clustering applies the same idea to learning:
it organises a federated learning process around whichever neighbours are reachable at a given moment~\cite{DBLP:journals/iot/DominiFAVE26}.

\section{IoT Ecosystems and Robot Swarms}
\label{sec:target-environments}

\subsection{Pervasive IoT Systems}
\label{subsec:iot-systems}

The term \emph{pervasive} refers to computing embedded throughout everyday physical settings,
following Weiser's vision of ubiquitous computing integrated into daily activities~\cite{Weiser1991Computer}.
Pervasive computing develops this vision through interconnected devices and services that respond to their surroundings~\cite{Satyanarayanan2001Pervasive}.
In the systems considered here, distributed sensors and actuators provide this connection between computation and the physical setting.

\ac{IoT} ecosystems~\cite{DBLP:journals/cn/AtzoriIM10} populate the continuum with large numbers of sensing and actuating devices,
connected through links with different bandwidth, latency, and reliability.
%
Individually, such devices run comparatively simple sensing or actuation loops.
%
Coordinating many of them towards a shared goal -- monitoring a building,
a field,
or a city district -- produces the collective behaviour an \ac{IoT} deployment is built for.
%
The set of devices that sustains this collective behaviour is not fixed.
Devices join and leave as they move,
fail,
or run out of power,
so the computation must survive changes in its own set of participants.

The deployment mechanism must continuously decide which devices host each part of the computation.
%
Dynamic \ac{IoT} deployment reconfiguration has been studied as a system-level self-organisation problem,
in which devices collectively decide how to redistribute computation as they join,
leave,
or change state~\cite{DBLP:journals/iot/FarabegoliPCV24}.
%
Simulation-based methodologies allow reconfiguration strategies to be evaluated before the more costly trials on physical infrastructure~\cite{DBLP:journals/iotj/CasadeiFPPSV22}.

\subsection{Swarm Robotics}
\label{subsec:swarm-robotics}

Swarm robotics studies large groups of relatively simple robots that achieve complex behaviour through local interaction and self-organisation~\cite{DBLP:journals/swarm/BrambillaFBD13,DBLP:journals/sensors/DiasSFVCP21}.
%
Throughout this thesis, \emph{self-organisation} denotes a process in which order at the global level of a system arises solely from local interactions among its components,
without external direction or a central controller --
the sense established for biological collectives by Camazine et al.~\cite{DBLP:books/daglib/0032897}.
%
De Wolf and Holvoet distinguish self-organisation from emergence:
the former concerns how a system organises itself,
while the latter concerns properties that arise at the collective level.
A system can exhibit either without the other~\cite{DBLP:conf/atal/WolfH04}.
%
A robot swarm occupies the mobile end of the continuum.
As robots move, the ad hoc network connecting them changes with their positions.
%
ALLIANCE is an early example of fault-tolerant cooperation among multiple robots.
It organised a team of behaviour-based robots so that tasks could be reassigned and individual failures tolerated without central coordination~\cite{parker1998alliance}.

Programming a swarm directly in terms of individual robot behaviours does not scale well as the swarm grows.
This limitation motivated dedicated languages and frameworks that express swarm behaviour at a higher level.
%
Buzz provides swarm-oriented primitives -- neighbourhood queries,
virtual stigmergy,
robot-to-robot synchronisation -- on top of a small imperative core~\cite{buzz-robot},
while Meld takes a declarative, logic-based approach and derives single-robot behaviour by compiling rules stated over the whole ensemble~\cite{meld-robot}.
%
Voltron provides team-level programming for drone sensor networks~\cite{voltron-robot}.
Actor-based abstractions have also been proposed for swarm robotic software,
isolating per-robot state behind message passing~\cite{DBLP:conf/iros/YiDLD0WY20}.
%
The \texttt{micros\_swarm\_framework} package extends the \ac{ROS} with swarm-specific support.\footnote{ROS project: \url{https://www.ros.org/}; package documentation: \url{https://wiki.ros.org/micros_swarm_framework}.}
Toolkits such as PySwarming provide reusable implementations of common swarm algorithms~\cite{DBLP:journals/jossw/AndradeFS23}.

Many of these approaches have been evaluated on a shared set of experimental platforms.
%
The Kilobot is a low-cost robot designed specifically to be deployed in the large numbers that swarm algorithms assume~\cite{DBLP:conf/icra/RubensteinAN12},
and the Kilogrid testbed extends it with a virtual sensing and communication substrate that lets a swarm of Kilobots be reconfigured between experiments without touching the hardware~\cite{valentini2018kilogrid}.
%
Where physical swarms of the required size are impractical,
ARGoS provides a modular, multi-engine simulation infrastructure built specifically for large swarms~\cite{pinciroli2012argos},
and Webots offers a general-purpose mobile-robot simulator with a graphical front-end~\cite{Michel2004}.
Both simulators allow swarm algorithms to be evaluated at scales that would be costly to reproduce on real robots.

\subsection{Collective Adaptive Systems and Their Deployment}
\label{subsec:collective-adaptive-systems}

\ac{IoT} ecosystems and robot swarms are two instances of a broader class,
called \emph{Collective Adaptive Systems} (CAS)\acused{CAS}:
systems composed of large numbers of autonomous, interacting entities whose collective behaviour must continue to meet its objectives despite changes in membership,
environment,
and goals~\cite{DBLP:journals/sttt/NicolaJW20}.
%
For these systems, correctness includes the collective's ability to meet its objectives as participants and topology change.

SCEL~\cite{DBLP:journals/taas/NicolaLPT14} supports changing ensembles of interacting components.
%
Its communication model is attribute-based:
an interaction reaches the components whose run-time attributes satisfy a predicate.
Ensembles form and dissolve as those attributes change.
%
Membership is thus decided by local interactions alone,
making ensemble formation self-organising in the sense defined in \cref{subsec:swarm-robotics}.
%
The language comes with a formal semantics,
so the behaviour of a system can be reasoned about as its ensembles reconfigure.

Architectural models can also make reconfiguration part of system behaviour,
as proposed for self-managed systems~\cite{DBLP:conf/icse/KramerM07}.
%
The DReAM framework instantiates this idea for \ac{CAS} specifically,
modelling dynamic reconfiguration as part of a system's architecture,
with a formal semantics that supports reasoning about the system as it reconfigures~\cite{DBLP:journals/sttt/NicolaMS20}.
%
Macroprogramming expresses the behaviour of a collective as a whole and provides programming abstractions for engineering \ac{CAS} at scale~\cite{DBLP:journals/csur/Casadei23}.

Deploying \ac{CAS} across the continuum raises two challenges.
%
First, computation and coordination logic must be assigned to heterogeneous hosts,
from constrained sensor nodes to gateways and cloud servers.
Mobility and intermittent connectivity can invalidate these assignments.
%
Second, coordination must continue to meet the collective's objectives as devices join or leave.

An architectural model must therefore identify units of computation that can be placed independently
and allow their host assignments to be revised at run time.
Microservices, functions, and actors provide useful deployment units,
but their usual deployment mechanisms leave unresolved how to separate a logical device's execution roles and reassign them across constrained, changing hosts
(\cref{subsec:paradigm-limitations}).

\section{Architectural Paradigms for Pervasive Systems}
\label{sec:architectural-paradigms}

Microservices, \ac{FaaS}, and actors structure applications into independently deployable units of different kinds.
All three have been adapted to edge and pervasive settings,
where small units can help exploit constrained resources and limit the amount of code and state that must move during reconfiguration.
Their deployment mechanisms differ in runtime requirements,
state management,
and control over placement.
These differences affect support for independent component placement and runtime reassignment.

\subsection{Microservices and FaaS at the Edge}
\label{subsec:microservices-faas-edge}

Microservices structure an application as a set of small services,
each running in its own process,
communicating through lightweight protocols,
and deployed,
scaled,
and replaced independently of the others~\cite{DBLP:books/sp/17/DragoniGLMMMS17}.
%
Independent deployability makes the model attractive for the continuum:
a unit that can be deployed on its own can,
in principle,
be placed on either an edge node or a cloud host.
%
Osmotic computing develops this observation into an architectural vision,
in which microservices migrate between edge and cloud infrastructure in response to resource availability and application requirements,
by analogy with osmotic pressure balancing concentrations across a membrane~\cite{DBLP:journals/cloudcomp/VillariFDRR16}.

\ac{FaaS} pushes the decomposition one step further,
structuring applications as stateless functions that are triggered by events and whose provisioning,
scaling,
and lifecycle are delegated entirely to the platform~\cite{DBLP:books/sp/17/BaldiniCCCFIMMRSS17}.
%
Fine granularity and demand-driven activation suit edge workloads,
which are often bursty and tied to local events.
Dedicated edge platforms include serverless prototypes for edge infrastructure~\cite{DBLP:conf/icfc/BaresiM19}
and tinyFaaS, which reduces the platform to fit a single constrained edge node by removing the cluster-level mechanisms that cloud \ac{FaaS} platforms assume~\cite{DBLP:conf/icfc/PfandzelterB20}.

Deployment unit and binding time are two dimensions in Crnkovic et al.'s classification of software component models~\cite{DBLP:journals/tse/CrnkovicSVC11}.
They help distinguish the two paradigms:
a microservice is a long-lived component bound to its host at deployment time,
whereas a function is bound at invocation and lives only for the duration of the call.
%
Typical implementations require a managed runtime -- a container orchestrator or a \ac{FaaS} platform -- on every candidate host,
restricting which parts of the continuum they can reach.

\subsection{The Actor Model at the Edge}
\label{subsec:actor-model-edge}

The actor model structures a concurrent system as a collection of actors:
isolated units of state and behaviour that interact only by asynchronous message passing,
and can create further actors in response to the messages they receive~\cite{DBLP:conf/ijcai/HewittBS73}.
%
Agha later developed the model into its canonical formal account,
in which the actor is the universal unit of both computation and distribution~\cite{DBLP:books/daglib/0066897}.
%
Because actors share no memory,
the same abstraction covers concurrency within a node and distribution across nodes,
and an actor can in principle be placed on any node able to deliver its messages.
%
An individual stateful object can thus serve as a deployment unit.

Erlang is an established industrial implementation of the model:
an Erlang node runs thousands of lightweight, isolated processes,
organised into supervision hierarchies that restart the processes that fail~\cite{DBLP:journals/cacm/Armstrong10}.
%
Decades of production use in telecommunications provide evidence that actor boundaries support fault isolation at scale in unreliable distributed settings.

Modern actor runtimes have made placement the platform's responsibility.
%
Orleans, for instance, activates actors on demand,
recovers them after failures,
and reclaims them when idle,
without requiring the application to manage their placement~\cite{DBLP:conf/cloud/BykovGKLPT11}.
%
This location transparency allows application code to address an actor independently of its current host.
%
In pervasive settings the model has been applied directly,
as in the actor-based framework for swarm robotic software already discussed in \cref{subsec:swarm-robotics},
which isolates per-robot state behind message passing~\cite{DBLP:conf/iros/YiDLD0WY20}.

\subsection{Limitations for Fine-Grained, Dynamic Deployment}
\label{subsec:paradigm-limitations}

Common implementations of these paradigms rely on managed runtimes whose requirements restrict the hosts they can use.
For containerised microservices,
each candidate host must support a container runtime and participate in an orchestration infrastructure.
This excludes many constrained devices at the edge (\cref{subsec:continuum-characteristics}).
Rescheduling also moves the service as a whole;
its internal sensing, state management, or coordination tasks are not independently deployable unless the application is decomposed further.

\ac{FaaS} provides smaller, short-lived units,
but persistent application state is normally managed by backing services.
If those services remain in the cloud,
edge execution still incurs wide-area round trips to access them.
%
Actors keep state with computation,
and runtimes such as Orleans show that placement can be automated.
Such automation depends on the runtime's placement policy and supported hosts.
It does not by itself separate an actor's computation,
state,
and communication into independently placeable components.
%
For the systems considered here,
the remaining requirement is to describe that finer decomposition and its host assignments explicitly,
so deployment can change without rewriting the collective behaviour.

\subsection{Pulverisation}
\label{subsec:pulverisation-background}

Pulverisation separates a collective system's logical organisation from the physical infrastructure that executes it~\cite{DBLP:journals/fi/CasadeiPPVW20}.
A \emph{logical device} represents an application participant,
such as a sensor node or robot.
Its components can run on several physical hosts;
one host can serve several logical devices.
Logical neighbourhoods describe application interactions;
the infrastructure supplies the paths that realise them.

Casadei et al.~\cite{DBLP:journals/fi/CasadeiPPVW20} decompose each logical device into five component roles.
\emph{Sensing} acquires observations from the physical setting,
and \emph{actuation} applies the actions computed by the application.
\emph{Behaviour} evaluates the application logic using sensor readings,
stored state,
and information from neighbouring logical devices.
\emph{State} retains the information needed between computation steps,
while \emph{communication} exchanges information with neighbours.
These roles provide separate deployment units with the dependencies shown in \cref{fig:pulverisation-components}.

\begin{figure}[tbp]
    \centering
    \input{figures/pulverisation-components}
    \caption[The five component roles of a logical device]{The five component roles of a logical device in the original pulverisation model~\cite{DBLP:journals/fi/CasadeiPPVW20}. Grey lines represent dependencies between roles, and red dotted lines communication with neighbouring logical devices; colours distinguish logical devices. The boundary denotes a logical participant; its components can be hosted on different physical devices.}
    \label{fig:pulverisation-components}
\end{figure}

A deployment assigns each component to a physical host that can support it.
The assignment must respect computational and memory requirements,
provide access to the relevant sensors or actuators,
and maintain communication between dependent components.
For example,
a robot can retain sensing and actuation on board while a nearby edge server executes its behaviour component.
Sensor readings are sent to the server,
which computes actions and returns them to the robot.
The robot remains one logical participant.
The additional communication affects latency and resource use,
so the suitability of this assignment depends on the task and the available links.

The original model distinguishes \emph{thick} hosts, which can execute computation,
possibly on behalf of several logical devices,
from \emph{thin} hosts, which can carry sensors and actuators but cannot compute~\cite{DBLP:journals/fi/CasadeiPPVW20}.
%
\Cref{fig:pulverisation-deployments} shows four deployments of the same roles,
ordered by how many of them move to a shared host.
In a peer-to-peer deployment,
each logical device runs entirely on its own host and exchanges messages with its neighbours directly (\cref{fig:pulverisation-deployments-p2p}).
A broker-based deployment moves only the communication components to a shared host,
as in publish/subscribe \ac{IoT} protocols such as MQTT (\cref{fig:pulverisation-deployments-broker}).
%
Moving the state components there as well concentrates the system's data in the cloud,
while each device still evaluates its own behaviour (\cref{fig:pulverisation-deployments-cloud}).
When devices are thin hosts,
behaviour also moves to the shared host,
and each device retains only sensing and actuation (\cref{fig:pulverisation-deployments-thin}).
%
The peer-to-peer deployment requires every device to execute its behaviour component.
A battery-powered sensor node may lack the computational resources to do so,
which rules that deployment out on such hardware.

Solid boxes are hosts and dotted boxes are components; colours distinguish logical devices, as in \cref{fig:pulverisation-components}. From (a) to (d), an increasing number of roles moves to a shared host.}

Farabegoli et al.~\cite{DBLP:journals/fgcs/FarabegoliPCV24} add declarative runtime remapping.
PulvReAKt describes component requirements and host capabilities separately from application behaviour.
Its middleware can relocate a component when host capabilities change,
provided the new host meets the component's requirements.
The five-role decomposition stays fixed through these changes.

\Cref{chap:pulverization} generalises the fixed roles to components derived from a macro-program's data-flow structure
and develops the model's formal semantics and deployment-independence proof.
