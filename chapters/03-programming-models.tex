\chapter{Programming Models for Large-scale Distributed Systems}
\label{chap:programming-models}

Programming collective systems across the edge-cloud continuum requires abstractions for describing how their participants work together.
%
Macroprogramming expresses this behaviour in a global program from which the code executed by individual participants is derived.
%
This chapter examines aggregate computing, choreographic programming, and multitier programming.
%
It also covers monads, effects, and capabilities for expressing coordination obligations.

\section{Macroprogramming}
\label{sec:macro-programming}

The architectural paradigms discussed in \cref{sec:architectural-paradigms} -- microservices, \ac{FaaS}, actors -- organise software around individual deployment units~\cite{DBLP:journals/tse/CrnkovicSVC11}.
Runtime support can automate their placement,
but the programmer must still define how those units cooperate.
%
In a \ac{CAS}, cooperation must also tolerate changing membership~\cite{DBLP:journals/sttt/NicolaJW20}.
%
A monitoring service spread over a building,
or a coordinated task assigned to a robot swarm,
is specified by what the whole collective achieves.
%
With node-centric code,
the developer must establish how individual behaviours combine to meet that specification,
including when devices join or leave.

\begin{figure}
    \centering
    \input{figures/macroprogramming}
    \caption{Macroprogramming, adapted from Casadei~\cite{DBLP:journals/csur/Casadei23}. At the macro level, macro-abstractions relate the goals of a macro-program to observables of the system as a whole. A macro-to-micro mapping derives the programs executed by individual entities, whose effects and emergent behaviour determine the macro-observables.}
    \label{fig:macroprogramming}
\end{figure}

In macroprogramming,
a program describes the collective's behaviour directly,
and a compiler or runtime derives the code each participant executes~\cite{DBLP:journals/csur/Casadei23}.
%
\Cref{fig:macroprogramming} relates this macro-to-micro mapping to the collective goals and observable behaviour of the system.
%
Macroprogramming encompasses approaches that differ in the form of their global specifications and in how those specifications determine individual devices' programs.
%
The collective is the unit of specification and reasoning;
the mapping to participant code is defined by the programming model.

This supports reasoning about properties such as protocol termination,
valid placement,
or field stabilisation at the level where the collective's objectives are stated~\cite{DBLP:journals/csur/Casadei23}.
Each guarantee depends on the assumptions of the corresponding model,
including its treatment of participant numbers,
communication,
and membership changes.

\section{Macroprogramming Paradigms}
\label{sec:foundational-paradigms}

The three paradigms provide a global description of a distributed computation from different starting points.
%
Aggregate computing derives node-local behaviour from a functional specification over computational fields;
choreographic programming derives one program per participant from a multiparty interaction protocol;
multitier programming derives per-tier code from a single program annotated with placement information.


\subsection{Aggregate Computing}
\label{subsec:aggregate-computing}

Aggregate programming describes a collective computation through \emph{computational fields}~\cite{DBLP:journals/csur/Casadei23,VIROLI2019100486}.
A field assigns a value to each participating device at each stage of execution.
For example,
temperature readings form a numeric field,
and a predicate identifying devices in a crowded area forms a boolean field.
The program describes how such fields are combined and transformed as their values change over time.

Fields are values on which functions operate:
one function's output can become another's input.
Arithmetic and comparison operators apply \emph{pointwise},
using the values at the same device.
Adding two numeric fields produces a field whose value at each device is the sum of its two local input values.
More complex collective behaviour can be expressed by composing these operations with reusable distributed functions~\cite{VIROLI2019100486,DBLP:conf/saso/BealV14a}.

The \texttt{distanceTo(source)} building block is one such function.
Its input is a boolean field that is true at the source devices.
Its output is a numeric field giving each device's distance to the nearest source,
with zero at the sources themselves.
Distance follows paths through the device network,
using a metric such as hop count or the length of neighbour links.
On a stable, connected network,
the distributed computation converges to these distances through repeated local exchanges.
For a line of three devices with unit-length links and a source at one end,
the resulting values are $0$, $1$, and $2$.
Pointwise addition combines values already available at each device;
\texttt{distanceTo} obtains information through interaction with other devices.

\Cref{lst:aggregate-channel} composes distance fields to identify a \emph{channel} between a single source and a single destination~\cite{DBLP:journals/lmcs/PianiniCVMZ21}.
The notation is aggregate pseudocode:
each variable denotes a field,
and each device evaluates its own contribution.
The parameter \texttt{width} is a non-negative value used throughout the network.

\begin{lstlisting}[
  language={},
  numbers=none,
  basicstyle=\ttfamily\footnotesize,
  columns=fullflexible,
  captionpos=b,
  caption={Aggregate pseudocode for a channel between two devices.},
  label={lst:aggregate-channel},
]
fromSource = distanceTo(source)
fromDestination = distanceTo(destination)
between = distanceBetween(source, destination)
channel = fromSource + fromDestination <= between + width
\end{lstlisting}

The first two lines compute distances to the endpoints.
The third computes their shortest separation and disseminates it across the network.
At each device,
the sum of the first two fields is the length of a shortest source--destination walk constrained to pass through that device.
The final comparison selects devices for which this length exceeds the shortest endpoint-to-endpoint distance by at most \texttt{width}.
With \texttt{width} equal to zero,
it selects devices on shortest paths;
larger values admit longer detours.
Thus \texttt{width} bounds excess path length,
not the geometric distance from a path.
\Cref{fig:ac-blocks-composition} illustrates this composition.

    \centering

    \input{figures/ac-blocks-composition.pdf_tex}
    \caption{Composition of computational fields in the \emph{channel} building block. The sum of distances to \emph{Source} and \emph{Destination} is compared pointwise with their shortest separation, computed by \texttt{distanceBetween}, plus \emph{Width}. The result marks devices whose excess path length is at most \emph{Width}.}
    \label{fig:ac-blocks-composition}
\end{figure}

The field calculus formalises aggregate computation as a minimal, universal functional model with corresponding local and aggregate semantics~\cite{VIROLI2019100486}.
Its higher-order extension supports fields and field-producing programs as first-class values~\cite{AVDPB-TOCL2019}.
The eXchange Calculus (XC) expresses state evolution and neighbour interaction through a single \texttt{exchange} construct~\cite{DBLP:journals/jss/AudritoCDSV24}.
Languages and runtimes that implement aggregate computation are described in \cref{subsec:cas-platforms}.

\subsubsection{Execution Model}
\label{subsubsec:ac-execution-model}

At the device level,
an aggregate computing system consists of a set of devices,
each executing an instance of the same aggregate program.
%
Each device can exchange messages with the subset of devices within its communication range,
called its \emph{neighbours}.
%
The execution model assumes bidirectional communication links between devices,
although messages may be lost or delayed,
reflecting the unreliability of wireless communication.
%
Time-fluid scheduling allows each device to adapt its execution rate to local conditions~\cite{DBLP:journals/lmcs/PianiniCVMZ21}.
%
In \cref{fig:ac-architecture}, the shaded area on the left represents the collective system,
composed of multiple devices (circles) that interact through local communication (lines);
on the right,
a single device is shown in detail to highlight its round-based execution model.
%
Each device operates asynchronously,
repeatedly performing \emph{sense-compute-interact} rounds.

\begin{figure}[t]
    \centering
    \input{figures/ac}
    \caption{
        Distributed system architecture for aggregate computing.
        Each device executes an instance of the aggregate program, interacting with its neighbours through local communication.
        The collective behaviour emerges from the composition of individual device computations and interactions.}
    \label{fig:ac-architecture}
\end{figure}

\paragraph{Sense.}
During the \emph{sense} step,
the device collects environmental data through its sensors, if any,
and stores the readings for use in the macro-level computation.
%
It then receives messages from its neighbours,
which carry the collective information needed for the computation.
%

\paragraph{Compute.}
In the \emph{compute} step,
the device applies the macro-program logic against the computational context assembled during \emph{sense}:
(i) the local sensor readings;
(ii) the messages received from neighbours;
and (iii) the device's own state from past computations.
%
Given these inputs,
the device evaluates the aggregate program,
producing a \emph{new local state},
\emph{messages for neighbours},
\emph{prescriptive actions},
and an \emph{output value}.
%
The device stores the new state for use in the next round,
places the messages in the outgoing message buffer for the \emph{interact} step,
and executes the prescriptive actions against its actuators, if any;
the output value represents the device's contribution to the collective computation.

\paragraph{Interact.}
During the \emph{interact} step,
the device inspects the outgoing message buffer and sends the corresponding message to each reachable neighbour.
%
At the end of the \emph{interact} step,
the device completes the round,
and typically sleeps for a period before starting the next one.

\paragraph{State and neighbourhood operations.}
The language provides operations for using the information available during a round.
\texttt{rep} retains and updates local state across rounds;
each device maintains its own value for each occurrence of the construct.
\texttt{nbr} makes the values of an expression from neighbouring devices available to the local computation.
A neighbourhood reduction combines these contributions,
for example by taking their minimum or sum.
ScaFi provides \texttt{foldhood} for such reductions.
The \texttt{branch} construct restricts a computation to devices taking the same branch of a condition,
allowing different parts of the network to execute different field computations~\cite{VIROLI2019100486,casadei2022scafi}.

\paragraph{Alignment and recovery.}
\emph{Alignment} associates exchanged values and retained state with the expressions that produced them.
A device uses a neighbour's value for a field expression only when the corresponding evaluations are aligned,
including the branch of the program they are executing.
The domain of each expression remains well defined when devices enter or leave a branch or when the network partitions and reconnects~\cite{VIROLI2019100486,AVDPB-TOCL2019}.

Field-based coordination supports self-organisation through these local interactions.
\emph{Self-stabilisation} additionally concerns recovery:
a computation is self-stabilising if it converges from an arbitrary state to a correct output once its inputs and environment become stable,
under the execution assumptions of the model.
For the reusable building blocks,
convergence requires that devices continue to execute and exchange information.
Their composition preserves self-stabilisation under the conditions established for those blocks~\cite{DBLP:conf/saso/BealV14a,DBLP:journals/tomacs/ViroliABDP18}.

This execution model is platform-independent:
a deployment may combine devices with different hardware architectures,
operating systems,
and runtime environments,
provided each executes a complete instance of the same aggregate program and supports the \emph{sense-compute-interact} cycle.
%
The collective logic therefore stays the same across heterogeneous devices,
but every platform must supply its own support for sensing and actuation,
for executing the program locally,
and for communicating with neighbours.
%
Offloading parts of a device's computation requires an additional deployment model,
such as the pulverisation approach described in \cref{subsec:pulverisation-background}.

\subsubsection{Application Scenarios}
\label{subsubsec:ac-application-scenarios}

Alignment, \texttt{nbr}/\texttt{rep}, and self-stabilising building blocks are used across several kinds of collective system.
%
Beal and Viroli make this reuse explicit with a shared library of aggregate building blocks for gradients, aggregation, time summarisation, and partitioning.
These blocks compose into higher-level behaviours such as crowd monitoring,
where a population of mobile devices is tracked and collectively warned away from dense areas without any device observing the entire system~\cite{DBLP:conf/saso/BealV14a}.

Swarm robotics is a second recurring scenario:
teams of robots or drones that must explore an area,
cover it,
or converge on a shared spatial configuration using only local, range-limited communication,
matching directly the neighbourhood-based communication model of \cref{subsubsec:ac-execution-model}.
%
Buzz and Voltron both target this setting with language-level support for robot-to-robot synchronisation and drone sensor networks respectively~\cite{buzz-robot,voltron-robot},
and the broader swarm-robotics literature documents the same decentralisation requirements across a wide range of multi-robot systems~\cite{DBLP:journals/swarm/BrambillaFBD13}.

A third scenario applies the same constructs at the infrastructure layer:
smart-city and edge services composed of many small, heterogeneous devices that cannot be assumed to share a clock.
%
Time-fluid scheduling targets this setting,
letting each device pick its own execution rate~\cite{DBLP:journals/lmcs/PianiniCVMZ21}.
%
Simulation lets the deployment performance of such collective services be estimated before they are rolled out on real edge infrastructure~\cite{DBLP:journals/iotj/CasadeiFPPSV22}.

Learning provides further applications of collective computation.
\ac{RL} has been explored as a way to learn parts of the local behaviour within an aggregate program~\cite{aguzzi2022towards}.
Proximity-aware, self-federated learning uses field-based coordination to organise distributed training:
devices form clusters from local information about nearby participants~\cite{DBLP:journals/iot/DominiFAVE26}.
Here the aggregate program coordinates the learning process.

These scenarios share the sense-compute-interact cycle despite differences in hardware,
communication,
and collective goals.
Reusable building blocks retain their guarantees where the deployment satisfies the assumptions under which those guarantees were proved.

\subsection{Choreographic Programming}
\label{subsec:choreographic-programming}

In its basic form, choreographic programming describes the interactions among a fixed set of participants in a single global program.
%
Its industrial precursor, the W3C \emph{Web Services Choreography Description Language},
already described the interactions among a set of services from a single, global viewpoint,
but without an operational way to derive implementations guaranteed to conform to that description~\cite{WSCDL}.
%
Montesi's \emph{Kickstarting Choreographic Programming} turned the idea into a programming discipline,
building on an older line of work that bridged interaction-oriented and process-oriented descriptions of choreographies~\cite{Montesi:2014,10.1109/SEFM.2008.11}.
%
That work draws on process algebra's treatment of interaction as a basis for describing concurrent systems~\cite{10.1016/j.tcs.2004.07.036}.
%
\emph{Endpoint projection} compiles it automatically into one program per participant;
for well-formed choreographies,
the derived programs satisfy properties such as deadlock freedom by construction~\cite{10.1145/2429069.2429101}.

Later work turned this operational idea into typed calculi.
%
An evaluation of choreographies against a set of concurrent algorithms identified the differences between the model and ordinary source code~\cite{CruzFilipe:2016}.
Procedural choreographic programming reduced these differences by adding familiar syntax and imperative control flow~\cite{CruzFilipe2017}.
%
Dynamic choreographies relax a different assumption, that a role's projected code cannot change once deployed,
letting delimited fragments of a participant's behaviour be replaced by new code at run time while keeping deadlock and race freedom across the update~\cite{Preda:2017}.
%
Process polymorphism relaxes the assumption of a fixed participant set,
letting a single choreography be written once and instantiated for a number of participants decided later~\cite{GRAVERSEN_HIRSCH_MONTESI_2024};
this permits specifications to be reused across collectives of different sizes (\cref{subsec:collective-adaptive-systems}).
%
\emph{Pirouette} introduced choreographic programming in a higher-order, typed functional setting~\cite{10.1145/3498684},
a direction developed further by subsequent work on functional choreographic programming~\cite{10.1007/978-3-031-17715-6_15};
Montesi's \emph{Introduction to Choreographies} provides a systematic account of the field~\cite{Montesi2023chor}.

On the implementation side, choreographies have increasingly been embedded as libraries inside general-purpose host languages.
%
Choral embeds choreographic programming in an object-oriented host language~\cite{10.1145/3632398},
while HasChor and ChoRus do the same for Haskell and Rust, respectively~\cite{10.1145/3607849,kashiwa2024chorus};
census-polymorphic choreographies~\cite{DBLP:journals/pacmpl/BatesKJSKN25} and lightweight choreographic cloud services~\cite{DBLP:conf/pepm/IonescuR26} extend this strategy to collectives of varying size and cloud deployments.
%
These library implementations are related to session types,
which check that each participant follows its prescribed communication protocol:
Scribble specifies interaction protocols with a syntax close to a choreography~\cite{DBLP:conf/icdcit/HondaMBCY11},
and the discipline has since been embedded in Rust~\cite{chen_et_al:LIPIcs.ECOOP.2022.22} and given a lightweight functional presentation~\cite{Lindley:2017}.
%
Jolie realises the resulting service-oriented protocols directly as a programming language~\cite{DBLP:books/sp/wsf14/MontesiGZ14}.
It supplies a runtime for the participating services.

\subsubsection{Execution Model}
\label{subsubsec:choreography-execution-model}

A choreography fixes, in one global program, both the set of participants -- named roles such as \texttt{Buyer} or \texttt{Seller} -- and the sequence of interactions between them.
%
An interaction statement names the value computed by a sender, the channel it travels on, and the receiver bound to it,
so the whole multiparty protocol can be read in one source program~\cite{Montesi:2014}.

\begin{figure}
    \centering
    \input{figures/epp}
    \caption[Endpoint projection applied to a two-party choreography]{Endpoint projection applied to a two-party choreography, adapted from Wiersdorf~\cite{wiersdorf2024chorex}.
    The global choreography (top) specifies a key-exchange-and-encryption protocol between \texttt{Alice} and \texttt{Bob} through statements of the form \texttt{Sender.expr() \textasciitilde> Receiver.(binder)}.
    Projection compiles it into one local program per role (bottom) and rewrites each interaction as a matching \texttt{send} or \texttt{receive} call.}
    \label{fig:epp}
\end{figure}

\emph{Endpoint projection} (EPP)\acused{EPP} turns this global description into an implementation, as \cref{fig:epp} illustrates for a two-party protocol.
For each role, \ac{EPP} erases every interaction the role is not party to and keeps only the statements -- sends, receives, local computation -- that mention it,
yielding one process per participant that, together, reproduce exactly the behaviour prescribed by the choreography~\cite{10.1145/2429069.2429101}.
%
Projection is sound only if the choreography satisfies a \emph{well-formedness} condition on conditionals and choice:
whenever a role's continuation depends on a decision taken elsewhere,
that decision must be communicated to it before the branch is taken,
so that no two projected processes can ever disagree about which branch of the protocol they are in~\cite{10.1145/2429069.2429101,Montesi2023chor}.
%
Under the model's communication assumptions,
\ac{EPP} produces deadlock-free and communication-safe programs from well-formed choreographies~\cite{10.1145/2429069.2429101}.
%
Typed accounts of \ac{EPP} strengthen this correspondence into a proof:
Pirouette derives, in Coq, that message-type soundness of the underlying language transfers through projection to deadlock freedom of the whole system~\cite{10.1145/3498684},
and functional choreographic programming develops the same correspondence for a higher-order setting~\cite{10.1007/978-3-031-17715-6_15}.
%
Library embeddings can implement \ac{EPP} as a function in the host language.
%
Choral compiles a choreography to a set of ordinary Java classes, one per role, so that projection happens ahead of time and the resulting endpoints are plain object-oriented libraries~\cite{10.1145/3632398}.
%
HasChor instead performs projection at run time, interpreting a choreography written as a free monad of located computations directly against each role's local view~\cite{10.1145/3607849}.
%
ChoRus uses the same run-time construction in Rust,
keeping the implementation within the host language's ecosystem~\cite{kashiwa2024chorus}.
%
Aggregate computing (\cref{subsubsec:ac-execution-model}) admits an open, dynamically changing neighbourhood,
with alignment and self-stabilisation supporting reasoning about the collective computation.
%
The basic choreographic execution model uses a statically named set of roles
and establishes correctness through the conditions on projection for those roles.
%
Process polymorphism relaxes this assumption,
letting the projected processes be instantiated for a participant count decided at run time~\cite{GRAVERSEN_HIRSCH_MONTESI_2024}.
This flexibility concerns the choice of participants;
tolerating arbitrary joins and departures during a protocol requires further support.
%
Dynamic choreographies relax a related but distinct assumption,
that a role's code, once projected, cannot change: delimited fragments of it can be replaced at run time without reopening the deadlock- and race-freedom guarantees already established~\cite{Preda:2017}.

\subsubsection{Application Scenarios}
\label{subsubsec:chor-application-scenarios}

The earliest and most direct application of the paradigm is service-oriented computing,
the setting the W3C Web Services Choreography Description Language targeted before an operational semantics existed for it~\cite{WSCDL}:
Jolie realises the resulting multiparty service protocols directly as a programming language,
in which each participating service's send, receive, and correlation logic is written and executed as ordinary source code~\cite{DBLP:books/sp/wsf14/MontesiGZ14}.
%
Session types also support protocol specification and verification:
Scribble describes multiparty session protocols in a syntax close to a choreography and checks an existing implementation against them~\cite{DBLP:conf/icdcit/HondaMBCY11},
a discipline since embedded directly in the type system of a systems language~\cite{chen_et_al:LIPIcs.ECOOP.2022.22}
and given a lightweight, purely functional presentation~\cite{Lindley:2017}.
%
More recent work applies choreographic programming to deployable cloud infrastructure.
Census-polymorphic choreographies target multi-tenant services whose participant count is not fixed until deployment~\cite{DBLP:journals/pacmpl/BatesKJSKN25},
and lightweight choreographic cloud services optimise the resulting projected processes for the resource constraints of real cloud deployments~\cite{DBLP:conf/pepm/IonescuR26}.
%
Typical protocols coordinate named services through interactions such as a purchase,
a two-factor login,
or a request-response exchange.
%
Their participants and interaction sequences are more tightly specified than in the open collectives that motivate aggregate computing (\cref{subsubsec:ac-application-scenarios}).
%
Process-polymorphic choreographies extend protocol descriptions to parameterised groups of participants.

\subsection{Multitier Programming}
\label{subsec:multitier-programming}

Multitier programming describes computations at several locations in a single source program.
%
The programmer annotates each fragment with the tier where it must run,
such as a client or server.
%
A compiler then slices the program accordingly~\cite{DBLP:journals/csur/WeisenburgerWS20},
as \Cref{fig:multitier-programming} illustrates for the canonical two-tier case.

\begin{figure}[t]
    \centering
    \input{figures/multitier-programming}
    \caption[Multitier programming]{
        Multitier programming, adapted from Weisenburger et al.~\cite{DBLP:journals/csur/WeisenburgerWS20}.
        Each fragment of a single program is annotated with the tier where it must run.
        The compiler then produces one program per tier: a browser client and a JVM server in this example.}
    \label{fig:multitier-programming}
\end{figure}

Links was among the first languages to apply this approach to the web.
It replaces the traditional split between client- and server-side code with a single functional language and an automatic slicing compiler~\cite{DBLP:conf/fmco/CooperLWY06}.
It follows earlier work that transformed sequential programs into multi-tier applications through source-to-source translation~\cite{10.1145/1040305.1040324}.
%
Hop applies the same principle with a Scheme-derived syntax~\cite{DBLP:conf/oopsla/SerranoGL06},
later revised as HopJS on top of JavaScript~\cite{10.1145/2951913.2951916}.
%
Ocsigen and its successor Eliom develop the same idea for OCaml~\cite{10.1145/1159876.1159889,Radanne:2016},
extended to whole applications by tierless web programming in the large~\cite{10.1145/3184558.3185953}.
%
Ur/Web couples tier slicing with a language designed specifically to rule out the injection and markup-mismatch errors common in hand-written web code~\cite{10.1145/2676726.2677004}.

Placement types record where a value resides and let the type checker verify where it can be used.
In the schematic notation \texttt{T on P},
the value has type \texttt{T} and resides on the logical peer \texttt{P}.
This identifies its location in the program's architecture;
the assignment of that peer to a physical host is a separate deployment decision.
%
The symmetric modal lambda calculus~\cite{10.5555/1018438.1021865,Sim94} gives each location its own modality
and types cross-tier access through intuitionistic modal logic.
\emph{ML5} develops the resulting calculus into a practical, type-safe distributed language~\cite{10.5555/1793574.1793585}.
%
ScalaLoci embeds placement types directly in Scala,
so the type system checks access across the declared architecture~\cite{DBLP:journals/pacmpl/WeisenburgerKS18},
and Multitier Modules extend the same discipline to placed components composed across module boundaries~\cite{Weisenburger:2019:Multitier}.
%
Type-safe dynamic placement with first-class placed values allows a value's location to change at run time while keeping placement checked statically~\cite{Zakhour:2023:TypeSafe}.
%
Exceptional asynchronous session types additionally check client-server communication protocols and their handling of failures~\cite{10.1145/3290341}.

\subsubsection{Execution Model}
\label{subsubsec:multitier-execution-model}

A compiler slices a multitier program into one deployable unit per tier,
together with the communication code the resulting units need to interact once they run on separate machines~\cite{DBLP:journals/csur/WeisenburgerWS20}.
%
Slicing involves two largely independent choices:
how fragments are assigned to tiers,
and how the resulting programs execute.
%
Explicit placement, the norm among the languages surveyed above, leaves the assignment of each program fragment to the programmer, expressed through whichever mechanism -- annotation, escaping and quoting, or a placement type -- the language provides.
%
Automatic placement instead derives the assignment from a static analysis of the whole program:
source-to-source transformation can assign primitive operations to tiers and insert the resulting remote calls~\cite{10.1145/1040305.1040324}.
%
Search-based tier assignment optimises the split for a metric such as offline availability~\cite{Philips:2018}.

Partitioned execution splits the program into independent components that run concurrently and communicate as peers over the network, the strategy adopted by Links, ML5, and ScalaLoci~\cite{DBLP:conf/fmco/CooperLWY06,10.5555/1793574.1793585,DBLP:journals/pacmpl/WeisenburgerKS18}.
%
Staged execution instead runs the tiers in sequence:
the server stage executes first and generates the program for the next stage,
splicing values it has already computed into the generated code before shipping it,
so the client program produced by Hop, Ur/Web, or Eliom already carries those server-side values~\cite{DBLP:conf/oopsla/SerranoGL06,10.1145/2676726.2677004,Radanne:2016}.

ScalaLoci~\cite{DBLP:journals/pacmpl/WeisenburgerKS18} checks remote access against the ties declared between peer types.
The placement type identifies where the value resides,
the architecture constrains who may access it,
and the compiler and runtime implement the required exchange.
The type alone does not specify a transport protocol or select a physical host.

Multitier languages provide several abstractions for these exchanges~\cite{DBLP:journals/csur/WeisenburgerWS20}.
%
Remote procedures are the predominant mechanism, letting a piece of code on one tier be invoked from another as if it were a local call.
%
Message passing exposes the underlying network protocol more directly.
%
Publish-subscribe and reactive programming propagate an event, or a changing value, from one tier to the others as it updates.
%
Shared state lets every tier read and write a single, server-coordinated data structure.

Remote procedures are most often specialised further into language-integrated queries,
letting a query against a remote database, or a call to a remote server, be written with the same syntax and type discipline as the rest of the program.
%
Kleisli's functional query system and \ac{LINQ} in C\# popularised the idea~\cite{wong2000kleisli,Torgersen:2007};
later work developed it for nested, heterogeneous data~\cite{10.1007/978-3-030-72019-3_21},
extended it with provenance tracking~\cite{10.1145/3315507.3330198},
and adapted it to temporal data~\cite{10.1145/3564719.3568690}.
%
A polymorphic \ac{RPC} calculus generalises the same principle beyond queries,
allowing the type of a remote procedure call to be polymorphic in the caller's location~\cite{CHOI2020102499}.
%
These abstractions allow the compiler to derive cross-tier communication from operations expressed in the source language.

Choreographic programming and multitier programming both derive several programs from a single source, but each guarantees a different property.
%
Endpoint projection guarantees that every process derived from a well-formed choreography is deadlock-free and communication-safe (\cref{subsubsec:choreography-execution-model}).
%
Tier slicing only guarantees that a value is used on a tier where it is available;
nothing in an ordinary placement type rules out a client and a server disagreeing about the state of a longer protocol.
%
Exceptional asynchronous session types add protocol checking,
including the handling of disconnections,
to client-server interactions~\cite{10.1145/3290341}.

\subsubsection{Application Scenarios}
\label{subsubsec:multitier-application-scenarios}

Most multitier languages target web client-server applications.
A browser tier communicates with a server tier over HTTP, and both are generated from the same source for their respective runtimes -- JavaScript for the browser and the host language's runtime for the server~\cite{DBLP:journals/csur/WeisenburgerWS20}.
%
A recurring extension includes a third tier in the same compilation unit:
Links and Ur/Web add language-level access to the database tier alongside client and server,
so that a query against persistent storage is placed and type-checked exactly like a call to the server itself~\cite{DBLP:conf/fmco/CooperLWY06,10.1145/2676726.2677004}.
%
A smaller number of languages move beyond the client-server pair.
%
ScalaLoci represents tiers as peer types,
letting a developer declare a custom architecture -- a pipeline, a ring, a master-worker scheme -- and have the compiler check that data only flows between the peers the architecture allows~\cite{DBLP:journals/pacmpl/WeisenburgerKS18}.
%
Multitier Modules extend the same peer-type discipline across module boundaries,
allowing a distributed architecture to be assembled from reusable subsystems~\cite{Weisenburger:2019:Multitier}.
%
AmbientTalk/R instead targets loosely coupled mobile ad hoc networks.
Peers export and discover each other's services directly,
and reactive programming abstractions propagate a changing value to whichever peers happen to be in communication range at a given moment~\cite{DBLP:conf/tools/CarretonMCM10}.
%
Most multitier languages fix the set of tiers, typically client and server, for the lifetime of the application.
Supporting a \ac{CAS} also requires accounting for changes in the participating devices (\cref{subsec:collective-adaptive-systems}).
%
Dynamic placement and ScalaLoci's peer types provide mechanisms for expressing changes of location and more general architectures,
respectively~\cite{Zakhour:2023:TypeSafe,DBLP:journals/pacmpl/WeisenburgerKS18}.

\subsection{Aggregate Programming Toolchains}
\label{subsec:cas-platforms}

The field calculus and XC define aggregate computation (\cref{subsec:aggregate-computing}).
%
Executing the specification on a device requires a programming language,
a runtime that carries out the sense-compute-interact cycle,
and, in practice, a simulator to check a design before it is deployed on hardware.
%
Several toolchains combine these elements for aggregate computing.

ScaFi realises the field calculus as an internal \ac{DSL} in Scala,
packaged with a companion runtime that runs the same aggregate program, unmodified, inside a discrete-event simulation or on physically distributed devices~\cite{casadei2022scafi}.
%
ScaFi is commonly simulated using Alchemist,
a discrete-event simulator built around chemical-inspired computational models~\cite{DBLP:journals/jos/PianiniMV13}.
%
Embedding gives aggregate programs access to the host language's tooling, libraries, and type system,
at the cost of a syntax constrained by Scala's own conventions.

Protelis is a dedicated, external language with syntax designed around fields and their composition~\cite{pianini2015protelis}.
%
ScaFi and Protelis target the JVM.
FCPP implements the aggregate execution model in C++,
supporting resource-constrained microcontrollers and embedded nodes through the same sense-compute-interact cycle (\cref{subsubsec:ac-execution-model})~\cite{DBLP:journals/scp/AudritoT24}.

An experience report covering more than a decade of aggregate-computing research reviews this ecosystem from the perspective of declarative programming.
It explains how the paradigm's declarative core allows language,
execution-dynamics,
middleware,
and deployment concerns to be addressed independently~\cite{10.1145/3678232.3678235}.

Aggregate processes extend the aggregate-computing model and its ScaFi implementation with concurrent collective computations.
A dynamic team of devices sustains each computation, and its spatial region can vary over time.
This supports the elastic membership of a \ac{CAS} (\cref{subsec:collective-adaptive-systems})~\cite{CASADEI2021104081}.
%
Simulation also supports deployment planning.
An Alchemist-based methodology estimates how deployment choices affect a collective service's performance before it runs on physical edge infrastructure~\cite{DBLP:journals/iotj/CasadeiFPPSV22}.

\section{Effects and Capabilities for Coordination}
\label{sec:advanced-linguistic-abstractions}
% NOTE: this section (monads, effects, capabilities) is the background for
% \cref{chap:language-and-coordination}: the capability material feeds \S6.2
% (Party), the monadic material feeds \S6.5 (ScalaTropy). Both are now written,
% so this section is load-bearing and should not be trimmed without checking
% what Chapter 6 cross-references.

Distributed coordination involves effects:
sending a message, waiting on a reply, failing partway through a protocol.
%
Monads encode and sequence effectful steps.
Direct-style approaches express operations in ordinary control flow,
with handlers interpreting them and effect or capability types checking their use.

\subsection{Monadic Effects}
\label{subsec:monadic-effects}

Functional languages use monads to represent effectful computations in their types and define how those computations compose.
%
Moggi identifies the monad as the structure common to state, exceptions, and non-determinism.
This reduces separate accounts of these effects to a shared sequencing operation~\cite{DBLP:journals/iandc/Moggi91}.
Wadler turns that structure into a programming idiom by placing a monad's operations behind a uniform interface~\cite{DBLP:conf/popl/Wadler92}.
%
Language-integrated queries also use monadic composition,
as in Kleisli's functional query system~\cite{wong2000kleisli} (\cref{subsec:multitier-programming}).

A monadic protocol composes operations such as sending,
waiting,
and branching on failure through the monad's bind operation.
The chosen monad defines how these steps are sequenced and interpreted.

\begin{figure}
    \centering
    \input{figures/monadic-pipeline}
    \caption{A monadic effect pipeline, illustrated with the Cloud Haskell process monad~\cite{DBLP:conf/haskell/EpsteinBJ11}.
    The protocol is written as a bind-sequenced local pipeline (top).
    The process monad executes the pipeline on its host node and performs the required network communication (bottom).}
    \label{fig:monadic-pipeline}
\end{figure}

Cloud Haskell uses monadic sequencing for coordination protocols (\cref{fig:monadic-pipeline}).
Its process monad sequences send, receive, and spawn operations across a network of nodes.
Distributed code is written as though these operations were local, while the monad performs the network communication~\cite{DBLP:conf/haskell/EpsteinBJ11}.
%
Session-typed channels admit the same treatment.
%
Session types are the type discipline for structured communication introduced by Honda, Vasconcelos, and Kubo:
a channel's type prescribes the order of sends and receives on it~\cite{DBLP:conf/esop/HondaVK98}.
%
Pucella and Tov encode a session type as a sequence of monadic actions,
so a protocol violation -- sending where the type expects a receive -- is a type error in the same sense as using a value of the wrong type~\cite{DBLP:conf/haskell/PucellaT08}.

\subsection{Direct-Style Effect Systems}
\label{subsec:direct-style-effect-systems}

Algebraic effects describe operations through a signature,
and handlers supply their interpretation.
The same effectful program can therefore be run under different handlers~\cite{plotkin2003algebraic,plotkin2009handlers}.

\Cref{lst:effect-request} declares two communication operations and uses them in a request.
The signature gives each operation's arguments and result type.
Here messages are strings,
and \texttt{Unit} is the type of the value \texttt{()},
returned by an operation with no informative result.
The program sends a message to Bob and returns the reply.
It uses ordinary sequential control flow;
the surrounding handler determines how the two operations are executed.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[
  language={},
  numbers=none,
  captionpos=b,
  caption={A request expressed through effect operations (pseudocode).},
  basicstyle=\ttfamily\footnotesize,
  columns=fullflexible,
  label={lst:effect-request},
]
effect send(peer, message): Unit
effect receive(): Message

def request():
    send(Bob, "ping")
    return receive()
\end{lstlisting}
\end{minipage}

When an operation is invoked,
control passes to its case in the selected handler.
The \texttt{resume(value)} expression continues the suspended program immediately after that operation,
using \texttt{value} as its result.
The handler remains active during the resumed computation.
This resumption is captured formally by continuation-passing semantics~\cite{Hillerström:2017}.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[
  language={},
  numbers=none,
  captionpos=b,
  caption={Network and simulated interpretations of the same request (pseudocode).},
  basicstyle=\ttfamily\footnotesize,
  columns=fullflexible,
  label={lst:effect-handlers},
]
handler Network:
    send(peer, message):
        transport.send(peer, message)
        resume(())
    receive():
        resume(transport.receive())

handler Simulated:
    send(peer, message): resume(())
    receive(): resume("pong")

handle request() with Network
handle request() with Simulated
\end{lstlisting}
\end{minipage}

In \cref{lst:effect-handlers},
\texttt{transport} supplies the underlying network operations.
The network handler sends the message,
resumes the request,
then waits for a reply when the request invokes \texttt{receive}.
The simulated handler performs no network communication:
it resumes after the send and supplies \texttt{"pong"} as the received value.
Both handlers leave the request's normal return value unchanged.
The second invocation therefore returns \texttt{"pong"}.
These listings use schematic notation for effects and handlers;
they are not programs in a specific implementation language.
\Cref{fig:effect-handlers} illustrates the two interpretations.

\begin{figure}
    \centering
    \input{figures/effect-handlers}
    \caption{Algebraic effect handlers applied to a coordination protocol.
    The effectful program (top) issues \texttt{send} and \texttt{receive} operations against a fixed signature without specifying their implementation.
    A network handler interprets them as remote communication, whereas a simulation handler executes the same operations locally.}
    \label{fig:effect-handlers}
\end{figure}

In OCaml,
handlers also allow concurrency schedulers to be implemented in the language,
with scheduling operations interpreted by a handler~\cite{DBLP:conf/pldi/Sivaramakrishnan21}.

Handlers determine how operations execute.
Effect systems check which operations a computation may invoke.
They record the effects a function may perform in its type,
allowing the type checker to verify their use.
This approach originates in the polymorphic effect systems of Lucassen and Gifford~\cite{lucassen1988polymorphic}.

Tracking a communication effect in this way corresponds to the discipline used for choreographic and multitier programs (\cref{subsec:choreographic-programming,subsec:multitier-programming}).
Orchard and Yoshida show an equivalence between an effect system for a concurrency calculus and a session-typed process calculus.
The sequence of effects recorded for one party is the session type prescribed for its channel~\cite{DBLP:conf/popl/OrchardY16}.

Exceptional asynchronous session types apply this correspondence to disconnection failures:
building session-typed channels on an effect-handler implementation lets a disconnection be handled by the same mechanism that handles any other effect, without leaving the session-typed discipline~\cite{10.1145/3290341}.

Capabilities extend this approach from what a computation may do to which resources it may access.
%
An object-capability system grants access to a resource only by handing over an unforgeable reference to it,
so the references held by a piece of code determine its authority~\cite{miller2003capability}.

Effekt realises this as a language design,
passing a capability for each effect explicitly as an argument so that effect safety follows from ordinary parameter passing~\cite{brachthaeuser2020effekt},
and effects-as-capabilities develops the same correspondence formally,
unifying effect handlers with lightweight effect polymorphism~\cite{10.1145/3428194}.

Capturing types bring capability tracking into Scala's type system,
recording which capabilities a value may use~\cite{DBLP:journals/toplas/BoruchGruszeckiOLLB23}.
%
Degrees of Separation applies the resulting capture-checking machinery to concurrency,
using capability types to rule out unsafe sharing between concurrent computations without a separate effect system~\cite{DBLP:journals/pacmpl/XuBO24}.
%
Both build on Scala 3, whose reference documents the language features this line of work extends~\cite{odersky2021scala3}.

For multiparty coordination,
monadic composition organises protocol steps,
handlers separate those steps from their execution,
and effect and capability types restrict the operations available to each computation.
These mechanisms support the protocol and placement checks introduced for choreographic and multitier programming (\cref{subsec:choreographic-programming,subsec:multitier-programming}).
